## Backend Specific

### Architecture Pattern

- **Layered architecture**: `api/endpoints` (routing + HTTP concerns) → `services` (business logic: `AIService`, `DataService`, `NLPService`, `GeminiFixService`, `ValidationService`, `minio_service`) → `models` (SQLAlchemy ORM) with `schemas` (Pydantic) for request/response typing.
- **Services are mostly stateless** with `@staticmethod` methods (e.g. `AIService.detect`, `DataService.preprocess`); model loading uses a **singleton registry** (`AIService._ModelRegistry`) that lazy-loads and caches weights once.
- **Dependency injection** is FastAPI-native: DB sessions are injected via `Depends(get_db)` (async generator in `{backend}/app/db/session.py`). No external DI container.
- **Dual DB access modes**: async SQLAlchemy (`AsyncSession`, aiomysql) in HTTP endpoints; **sync** SQLAlchemy (pymysql, `_sync_session()`) inside Celery tasks because workers are non-async.
- Routers are thin: each endpoint module exposes `router = APIRouter()` and is mounted with a prefix in `main.py`.

### Error Handling

- Endpoints raise `fastapi.HTTPException(status_code=..., detail=...)` for client/known errors (404 not found, 400 bad input, 503 Celery unavailable).
- Unexpected errors are caught, logged (`logger.exception`/`logger.error`), and re-raised as `HTTPException(500, detail=str(e))`.
- **Celery tasks** wrap work in try/except: on failure they mark `PipelineRun` as `failed` with `error_message`, log, then `raise self.retry(exc=exc)` (bounded `max_retries`).
- **Graceful degradation is a recurring pattern**: missing Celery → pipeline stays `pending` but API succeeds; missing model weights → IsolationForest fallback; missing WeasyPrint → raw-bytes PDF fallback; missing LLM → template report fallback.
- No project-wide custom exception classes detected; dataclasses (`AgentResult`, `FixSuggestion`, `ReportResult`, `SelectionResult`) carry structured results instead.

### Validation

- **Request validation** via Pydantic `BaseModel` request bodies declared either in `schemas/` or inline in the endpoint module (e.g. `StartAnalysisRequest`, `GenerateReportRequest`).
- **File validation** is manual in `upload.py` (extension/content-type allowlist, 100MB size cap, empty-CSV guard).
- **Domain/business validation** is config-driven: `ValidationService` + rule sets, with detection-side business rules in `{ai_services_detection}/configs/business_rules.yaml` and `default.yaml`.
- **JSON safety**: floats are sanitized (`NaN`/`Inf` → `None`) before persisting to MySQL JSON columns (`_sanitize_for_json` in tasks, `_clean` in `upload.py`).

## API Response Format

The API does **not** use a single global envelope; responses are **plain JSON objects shaped per endpoint**. Observed conventions:

- **Success** — endpoint-specific dicts, typically echoing the resource id and a human message, e.g.:
  ```json
  { "dataset_id": 12, "message": "File uploaded successfully" }
  { "analysis_id": 5, "pipeline_id": 9, "message": "Analysis started" }
  ```
- **List endpoints** — return a bare JSON **array** (e.g. `GET /analysis` → `[ {id, title, status, progress, metadata, pipeline_id}, ... ]`), not a wrapped object.
- **Result/detail endpoints** — flat objects with the full payload (e.g. `GET /analysis/{id}/results` returns `anomaly_scores`, `models_used`, `model_metadata`, `anomaly_count`, `anomaly_type_breakdown`, …).
- **Errors** — FastAPI default shape: `{ "detail": "<message>" }` with the appropriate HTTP status. Status usage: `400` invalid input, `404` not found, `400/503` for pipeline/Celery state conflicts, `500` unexpected.
- **Pagination** — minimal: list endpoints take a `limit` query param (`Query(default=10, ge=1, le=100)`); no cursor/offset envelope or total-count metadata detected.
- **Validation results** — the backend returns column-level `errors`/`warnings` with a `summary` block (`total_rows`, `valid_rows`, `invalid_rows`, `error_count`, `warning_count`); the frontend re-maps this to row-level structures.

> Not detected in this project: a shared response wrapper class, standardized error codes (beyond HTTP status), authentication enforcement on endpoints (JWT settings exist in config but no auth dependency is applied to routes).
