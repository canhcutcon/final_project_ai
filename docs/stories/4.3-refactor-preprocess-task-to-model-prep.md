# Story 4.3: Refactor preprocess_task to model prep

## Status

Approved

## Story

**As a** platform maintainer,
**I want** `preprocess_task` to consume the canonical Parquet and perform only ML preparation,
**so that** business cleaning and model prep are decoupled.

## Acceptance Criteria

1: `preprocess_task` reads `datasets.canonical_path` (no raw-CSV re-parse), applies encoding/scaling/feature prep only, and preserves its output contract to `detect_anomalies_task` (keys: `processed_obj`, `n_rows`, `n_cols`, `config`)
2: The business-cleaning behavior of `DataService.preprocess()` (DtypeCorrector, MissingValueHandler silent imputation) is removed from that function; equivalent user-visible cleaning now happens in Epic 3 services for the canonical path, and is re-applied inline in `preprocess_task`'s `canonical_path is None` fallback branch (Subtask 2.3) so the legacy quick-mode path keeps identical behavior — with a regression test proving detection F1 on the reference dataset does not degrade versus the pre-refactor baseline
3: `detect_anomalies_task`'s raw-label lookup uses the canonical Parquet instead of re-reading the original CSV from MinIO (readable values are now guaranteed by tier 1)
4: End-to-end integration test: upload → sheet/header → map → clean → confirm → detection completes with results and a generated report
5: "Quick mode" path still works: upload with a TDM whose mapping is fully remembered runs auto-map + deterministic cleaning + auto-confirm when zero required errors, then the same chain

## ⚠️ Risk note (read before implementing)

Epic 4's own Additional Notes call this "the riskiest change in the initiative (touches detection quality)" and require it to "land behind the quick-mode flag and only become the default after the F1 regression test passes." Treat the flag-gating and regression test (Task 4 below) as gating criteria for merging this story's behavior change to production, not as after-the-fact validation.

## Tasks / Subtasks

- [ ] Task 1 — Capture the pre-refactor F1 baseline (AC: 2) — **do this first, before changing any code**
  - [ ] Subtask 1.1 The detection platform already has baseline result files at `{ai_services_detection}/outputs/working_v10/v10_baseline_results.csv`, `{ai_services_detection}/outputs/working_v10/v10_results.csv`, and `{ai_services_detection}/outputs/working_v11/v11_results.csv` — use these as the F1 reference rather than re-running training; confirm which one (`v10` vs `v11`) reflects the model currently served in production (`{backend}/app/ml/models/v10/`, `v11/` per `source-tree.md`) and use that as the regression baseline
  - [ ] Subtask 1.2 Run the **current** (pre-refactor) `preprocess_task` → `detect_anomalies_task` path against the reference detection dataset and record the F1 score exactly as computed today, before touching `DataService.preprocess()` — this is the number Subtask 4.x's regression test compares against
- [ ] Task 2 — Refactor `preprocess_task` to read canonical Parquet (AC: 1)
  - [ ] Subtask 2.1 `{backend}/app/tasks/pipeline_tasks.py::preprocess_task` currently does: `dataset = db.query(Dataset)...` → `minio_service.get_file_stream(dataset.storage_path)` → `pd.read_csv(io.BytesIO(content))` → `DataService.preprocess(df_raw)` → write `_processed.parquet`. Change the source read to `minio_service.get_file_stream(dataset.canonical_path)` + `pd.read_parquet(io.BytesIO(content))` instead of the raw-CSV path — this requires `dataset.canonical_path` to already be set, which Story 4.2's complete-import gate guarantees for any dataset that reaches this task through the new flow
  - [ ] Subtask 2.2 Add a defensive check: if `dataset.canonical_path` is `None` (i.e. the dataset was launched via the legacy quick-mode `POST /api/v1/analysis` path from Story 4.2 Task 5, which doesn't go through Story 4.2's complete-import gate), fall back to the existing raw-CSV read — this is exactly what keeps NFR5's "quick mode" flow working (AC5) without forcing every caller through canonical-Parquet generation; document this fallback clearly since it's the seam between the old and new preprocessing tiers
  - [ ] Subtask 2.3 **(resolves the preprocess self-contradiction — do not skip)** Because Task 3 strips business cleaning (`DtypeCorrector`/`MissingValueHandler`) out of `DataService.preprocess()`, the fallback branch above would otherwise feed **raw, un-cleaned** CSV into a `preprocess()` that no longer cleans — silently degrading detection quality on exactly the legacy path this fallback exists to preserve. So the fallback branch (and **only** the fallback branch, when `canonical_path is None`) must re-apply the retired cleaning inline **before** calling `preprocess()`: read raw CSV → `DtypeCorrector().correct(df)` → `MissingValueHandler(...).handle(df)` → `DataService.preprocess(df)`. On the canonical path (`canonical_path` set) the data is already clean (Epic 3 + Story 4.2), so those two steps are skipped and `preprocess()` runs on already-clean data. Net effect: `preprocess()` itself is pure model-prep (AC1), while legacy quick-mode keeps byte-identical behavior to today. Keep `preprocess()` free of these correctors — do the inline cleaning in the fallback branch of `preprocess_task`, not back inside `preprocess()`.
  - [ ] Subtask 2.3 Preserve the exact output contract: `{"pipeline_id", "dataset_id", "processed_obj", "n_rows", "n_cols", "config"}` — `detect_anomalies_task` and downstream tasks must not need any changes to their consumption of this dict beyond what Task 3 requires
- [ ] Task 3 — Strip business-cleaning from `DataService.preprocess()` (AC: 2)
  - [ ] Subtask 3.1 `{backend}/app/services/data_service.py::preprocess()` currently runs, in order: `DtypeCorrector().correct(df)` → `MissingValueHandler(...).handle(df)` (silent imputation — this is the behavior Epic 4's Additional Notes and Epic 3's Additional Notes both flag as being "retired in Epic 4 Story 4.3") → per-column `LabelEncoder` on categoricals → `ScalerManager(...).fit_transform(df, "standard")`. Remove the `DtypeCorrector` and `MissingValueHandler` calls; **keep** the `LabelEncoder`/`ScalerManager` steps — those are legitimate model-prep (encoding/scaling), not business cleaning, per AC1's "applies encoding/scaling/feature prep only"
  - [ ] Subtask 3.2 Since business cleaning (missing-value handling, dtype correction) is removed from this function, the canonical Parquet it now reads (Task 2) must already be clean and correctly-typed — this is guaranteed by Epic 3's validation/cleaning services having run before Story 4.2's complete-import gate produces the canonical Parquet in the first place; `DataService.preprocess()` now only needs to handle numeric encoding/scaling of already-clean data, not fix bad data. **The one case where the input is not pre-cleaned is the legacy fallback branch — that branch does the cleaning itself, before calling `preprocess()` (Subtask 2.3), so `preprocess()` can still assume clean input in all cases.**
  - [ ] Subtask 3.3 Update `preprocess()`'s returned `summary` dict's `algorithms_used` list to drop `"DtypeCorrector"`/`"MissingValueHandler"` and reflect only `["LabelEncoder", "ScalerManager(Standard)"]`
  - [ ] Subtask 3.4 Do not delete `DtypeCorrector`/`MissingValueHandler` from `{ai_services_detection}/src/data/cleaning.py` itself — they may still be used by the offline training pipeline (`{ai_services_detection}/scripts/run_pipeline.py`) independent of this serving-side change; this story only changes what `{backend}/app/services/data_service.py::preprocess()` calls at serving time
- [ ] Task 4 — F1 regression test (AC: 2) — **gates this story's completion**
  - [ ] Subtask 4.1 Run the refactored path (canonical Parquet → stripped `preprocess()` → `detect_anomalies_task`) against the same reference detection dataset used in Task 1, and compare F1 against the recorded baseline
  - [ ] Subtask 4.2 Add this as a checked-in, re-runnable test/script (e.g. `{backend}/tests/test_detection_regression.py` or a script alongside `{backend}/scripts/benchmark_latency.py`'s convention) rather than a one-off manual comparison, so it can be re-run whenever `DataService.preprocess()` or the cleaning services change in the future
  - [ ] Subtask 4.3 If F1 degrades beyond an agreed tolerance, **do not proceed to making this the default path** — this is explicitly the gating condition from Epic 4's Additional Notes; keep the refactor behind the quick-mode flag (i.e. only reachable via Story 4.2's new complete-import flow, with legacy `POST /api/v1/analysis` still using the pre-refactor behavior via Task 2.2's fallback) until the regression is resolved
- [ ] Task 5 — `detect_anomalies_task` canonical-Parquet label lookup (AC: 3)
  - [ ] Subtask 5.1 `{backend}/app/tasks/pipeline_tasks.py::detect_anomalies_task` currently loads `raw_df` for human-readable labels via a **second** MinIO read of `dataset.storage_path` + `pd.read_csv(...)` (with a `try/except` that logs a warning and sets `raw_df = None` on failure). Change this to read `dataset.canonical_path` + `pd.read_parquet(...)` instead when it's set — the canonical Parquet already has human-readable values by construction (Story 4.2), so this both removes a redundant raw-CSV re-parse and is more correct than today's raw-CSV read (which could itself contain the same messy/unmapped values Epic 3 was built to clean)
  - [ ] Subtask 5.2 Preserve the same graceful-fallback behavior (`raw_df = None` with a logged warning) when `canonical_path` is unset (legacy quick-mode path) — do not make this a hard failure
- [ ] Task 6 — End-to-end integration test (AC: 4)
  - [ ] Subtask 6.1 `{backend}/tests/test_e2e_import_pipeline.py`: drive the full sequence — upload (Epic 2 Story 2.1) → sheet/header selection (Epic 2 Stories 2.2/2.3) → mapping confirm (Epic 1 Story 1.4) → cleaning (Epic 3 Stories 3.1–3.3, at least one applied fix) → complete-import (Epic 4 Story 4.2) → this story's refactored `preprocess_task`/`detect_anomalies_task` → assert an `AnalysisResult` with populated `anomaly_scores` and a generated `Report` exist at the end — mock Celery to run tasks synchronously/eagerly in the test rather than requiring a real broker, following whatever pattern this codebase's existing tests use for Celery-adjacent code (`conftest.py` stubs; check if `CELERY_TASK_ALWAYS_EAGER`-style config is feasible here, or call the task functions directly in sequence as plain Python calls, matching how `agent_fix_task.py`'s task function is just a decorated regular function that can be invoked directly in tests)
- [ ] Task 7 — Quick-mode auto-confirm path (AC: 5)
  - [ ] Subtask 7.1 For a dataset uploaded against a TDM whose mapping is **fully remembered** (Epic 1 Story 1.3's historical layer returns confidence 1.0 for every column via an exact header-signature match) and that has **zero required-column errors** after auto-mapping + deterministic cleaning (Epic 3 Story 3.2's rule-based fixers only — no LLM/prompt steps, keeping this path fast and deterministic), automatically run: auto-map (Epic 1 Story 1.3's `suggest_mapping` + auto-confirm since confidence is 1.0) → deterministic cleaning (Epic 3 Story 3.2's rule fixers) → auto-confirm (this story's `complete-import` logic from Story 4.2, invoked programmatically rather than via explicit user click) → the same Celery chain
  - [ ] Subtask 7.2 Implement this as an orchestration function (e.g. in `import_completion_service.py` from Story 4.2, or a new `quick_mode_service.py`) triggered right after upload when the conditions are met, rather than duplicating the mapping/cleaning/confirm logic — every step reuses the exact same functions Epics 1/3/this-epic already expose via their endpoints, just called directly instead of through separate HTTP round-trips
  - [ ] Subtask 7.3 If at any point the conditions aren't met (mapping isn't fully remembered, or required errors remain after deterministic cleaning), fall back to the normal interactive wizard flow rather than partially auto-processing and leaving the user confused about what happened — auto mode is all-or-nothing per import
- [ ] Task 8 — Tests
  - [ ] Subtask 8.1 Unit tests for the trimmed `DataService.preprocess()` (asserts `DtypeCorrector`/`MissingValueHandler` are no longer invoked, `LabelEncoder`/`ScalerManager` still are)
  - [ ] Subtask 8.2 Unit tests for `preprocess_task`'s canonical-vs-legacy source selection (Task 2.2's fallback) and `detect_anomalies_task`'s canonical-vs-raw label source selection (Task 5.2) — **including an explicit test that the fallback branch applies `DtypeCorrector`/`MissingValueHandler` inline (Subtask 2.3) while the canonical branch does not**, so the legacy-path cleaning can't silently regress

## Dev Notes

### Relevant Source Tree

- `{backend}/app/tasks/pipeline_tasks.py` — **the file this story's core changes land in**. `preprocess_task` (lines ~105-157 as of this writing): raw-CSV read from `dataset.storage_path` → `DataService.preprocess()` → write `_processed.parquet`; output dict `{pipeline_id, dataset_id, processed_obj, n_rows, n_cols, config}` consumed by `detect_anomalies_task`. `detect_anomalies_task` (lines ~163-247): reads the processed Parquet for the model input, **plus a second raw-CSV read** of `dataset.storage_path` (wrapped in try/except, `raw_df = None` on failure) purely to get human-readable labels for `AIService.detect(df, model_name=..., raw_df=raw_df)`. `launch_pipeline()` at the bottom fires the unmodified 5-task chain (`preprocess_task → detect_anomalies_task → fix_data_task → generate_report_task → export_pdf_task`) — this story does not touch `fix_data_task`/`generate_report_task`/`export_pdf_task`, per Epic 4's Additional Notes ("Celery chain's remaining tasks... are otherwise unchanged").
- `{backend}/app/services/data_service.py::preprocess()` — the function this story trims: currently `DtypeCorrector` → `MissingValueHandler` (silent imputation, config `{"cleaning": {"missing": {}}}`) → per-categorical-column `LabelEncoder` → `ScalerManager` (standard scaling). Imports `DtypeCorrector`/`MissingValueHandler`/`ScalerManager` lazily from `{ai_services_detection}/src/data/cleaning.py` and `transforms.py` via a `sys.path` append — this lazy cross-repo import mechanism is unchanged by this story, only which classes get called.
- `{ai_services_detection}/outputs/working_v10/v10_baseline_results.csv`, `v10_results.csv`, `{ai_services_detection}/outputs/working_v11/v11_results.csv` — existing F1 baseline artifacts to use for the regression test (Task 1/4), per `tech-stack.md`'s note "V10 F1≈0.88."
- `{backend}/app/services/ai_service.py::AIService.detect` — consumer of `raw_df` for human-readable label display; unchanged interface, only the source of `raw_df` changes (Task 5).
- `{backend}/app/tasks/agent_fix_task.py` — structural precedent for calling detection-platform code (`sys.path` manipulation, lazy imports) and for how Celery task functions can be invoked as plain Python functions in tests (useful for Task 6's E2E test).
- Story 4.2 (this epic) — the direct producer of `dataset.canonical_path`, which this story's `preprocess_task`/`detect_anomalies_task` consume; also the auto-confirm logic this story's quick-mode path (Task 7) invokes programmatically.
- Epic 1 Story 1.3's `suggest_mapping`/historical layer, Epic 3 Story 3.2's rule-based fixers — direct dependencies of the quick-mode auto path (Task 7).

### Patterns & Conventions

- **Backend architecture**: `pipeline_tasks.py` stays a Celery-task module calling into `services/` (`DataService`, and now indirectly `import_completion_service.py` from Story 4.2 for canonical-path awareness); this story does not restructure that layering, only what data source each task reads.
- **Sync DB / lazy imports inside Celery tasks**: unchanged conventions — `_sync_session()` (pymysql), lazy `from app.services... import ...` inside task bodies to keep worker startup fast, consistent with the rest of this file.
- **Graceful degradation / fallback paths**: this story adds a new instance of the established pattern (missing Celery → pending; missing model weights → IsolationForest; missing WeasyPrint → raw bytes) — here, missing `canonical_path` → fall back to the pre-refactor raw-CSV path, preserving NFR5's quick-mode guarantee.
- **JSON/Parquet sanitization**: `_sanitize_for_json` (NaN/Inf → None) in `pipeline_tasks.py` is unchanged and still applies to `detect_anomalies_task`'s output.
- **Testing convention for Celery tasks**: task functions are plain `@celery_app.task`-decorated Python functions that can be called directly (not just via `.delay()`) — this is how `agent_fix_task.py`'s logic is structured and should be leveraged for the E2E test (Task 6) rather than requiring a live Celery broker.
- **Error handling**: unchanged — each task's existing `try/except self.retry(...)` + `_update_pipeline(..., status="failed", ...)` pattern stays exactly as is; this story only changes what's read inside the `try` block, not the surrounding error handling.

### Tech Stack

- **Backend**: FastAPI/Celery[redis] >=5.3.0 (task chain, unchanged wiring), async/sync SQLAlchemy split (unchanged — `_sync_session()` inside tasks).
- **Data Processing**: pandas + PyArrow for canonical/processed Parquet I/O; scikit-learn's `LabelEncoder` (kept) — `DtypeCorrector`/`MissingValueHandler` (removed from the serving path, per AC2) come from `{ai_services_detection}/src/data/cleaning.py`, which this story does not delete, only stops calling from `data_service.py`.
- **ML**: XGBoost/PyTorch detection models — unaffected by this story except through the F1 regression test that verifies their input distribution hasn't shifted.
- **Testing**: pytest/pytest-mock; the F1 regression test and E2E integration test are the two highest-value, highest-effort tests in this whole initiative — budget accordingly.

### Notes from Previous Stories

- Story 4.2 produces `dataset.canonical_path` and the "quick mode" flag/legacy-path preservation this story's fallback logic depends on — this story cannot be correctly implemented without Story 4.2 already in place.
- Epic 3's Additional Notes explicitly named this story as where "silent imputation (the old `MissingValueHandler` behavior) is retired" — confirming the business-cleaning-removal scope described here was planned from Epic 3's own design, not invented ad hoc in this story.
- Epic 1 Story 1.3 (historical mapping layer) and Epic 3 Story 3.2 (rule-based fixers) are both prerequisites for this story's quick-mode auto-confirm path (Task 7) — that path is pure orchestration over existing functionality, not new business logic.

### Testing

- Test file location: extend `{backend}/tests/test_data_services.py` for the trimmed-`preprocess()` unit tests; new `{backend}/tests/test_detection_regression.py` for the F1 gate; new `{backend}/tests/test_e2e_import_pipeline.py` for the full-flow integration test; extend or add a quick-mode test file for Task 7.
- Framework: pytest + pytest-mock, following established conventions; the E2E test should call Celery task functions directly (not via `.delay()`/a live broker) per the pattern already usable from `agent_fix_task.py`'s structure.
- Test types required: unit (trimmed preprocess, source-selection fallbacks), regression (F1 gate — the most important test in this story), integration (full E2E flow), and quick-mode-path behavioral test. The F1 regression test is a **merge gate**, not just coverage — per Epic 4's explicit risk framing, do not consider this story done if it fails.
