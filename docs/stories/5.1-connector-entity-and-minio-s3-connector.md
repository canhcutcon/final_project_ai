# Story 5.1: Connector entity & MinIO/S3 connector

## Status

Draft

## Story

**As a** platform operator,
**I want** to register input/output connectors,
**so that** pipelines can receive and deliver data without manual uploads.

## Acceptance Criteria

1: `connectors` table + CRUD API/UI: name, `type: input | output`, `kind: manual | minio_s3 | ftp_sftp | http | email`, and kind-specific config; credentials are encrypted at rest and never returned by the API (write-only fields)
2: MinIO/S3 implemented first for both directions: input watches a configured bucket/prefix for new objects; output writes result files to a bucket/prefix; a "Test connection" action verifies credentials and access before saving
3: The `manual` kind wraps the interactive upload path as a pseudo-connector so a pipeline definition can start from manual uploads uniformly
4: `ftp_sftp`, `http`, `email` kinds are registered as enum values with clear "not yet implemented" responses (schema-ready, implementation deferred)
5: Unit tests: credential encryption round-trip, config validation per kind, test-connection success/failure paths

## Tasks / Subtasks

- [ ] Task 1 — Credential encryption approach (AC: 1) — **decide before modeling the table**
  - [ ] Subtask 1.1 `{backend}/requirements.txt` already has `cryptography>=42.0.0` (used today only as a transitive TLS/JWT dependency, per `tech-stack.md`) — no existing encryption-at-rest code exists anywhere in this codebase to reuse. Use `cryptography.fernet.Fernet` (symmetric, includes authentication) for connector credential encryption rather than adding a new dependency; the encryption key is env-provided (per Epic 5 Dependencies) — add `CONNECTOR_ENCRYPTION_KEY: str` to `Settings` in `{backend}/app/core/config.py`, following the existing `Settings`-field-per-secret convention (`GEMINI_API_KEY`, `MINIO_SECRET_KEY`)
  - [ ] Subtask 1.2 Document the key-rotation procedure (Epic 5 Dependencies explicitly calls for this) as a code comment near the encryption helper plus a short section in wherever this project keeps operational runbooks — re-encrypting all stored credentials under a new key is a data-migration concern, not just a config change; note this clearly rather than leaving it implicit
- [ ] Task 2 — `connectors` table (AC: 1)
  - [ ] Subtask 2.1 Add `Connector` ORM model (new `{backend}/app/models/connector.py`): `id, name, type (Enum: input|output), kind (Enum: manual|minio_s3|ftp_sftp|http|email), config (JSON — non-secret fields only), encrypted_credentials (Text, nullable — Fernet ciphertext, never the raw JSON), created_at, updated_at`, following the `Template`/`TargetDataModel` modeling style (unique `name`, JSON config column)
  - [ ] Subtask 2.2 New Alembic migration for `connectors` — blocked on Epic 1 Story 1.1's chain repair, same prerequisite as every other migration across this initiative; check whether Epic 4's migrations (canonical_path, etc.) have already landed and coordinate revision ordering
- [ ] Task 3 — Pydantic schemas with write-only credentials (AC: 1)
  - [ ] Subtask 3.1 `{backend}/app/schemas/connector.py`: `ConnectorCreate`/`ConnectorUpdate` accept a `credentials: dict | None` field (raw, only on write); `ConnectorOut` **never** includes `credentials` or `encrypted_credentials` — only `id, name, type, kind, config, created_at, updated_at`, plus a boolean `has_credentials: bool` so the UI can show "credentials configured" without ever exposing them, matching AC1's "never returned by the API"
  - [ ] Subtask 3.2 Per-`kind` config validation: a discriminated union or a `model_validator` on `ConnectorCreate` requiring `minio_s3`-specific fields (`endpoint, bucket, prefix, access_key` in `credentials`, `secret_key` in `credentials`) when `kind == "minio_s3"`, and rejecting unknown/missing fields per kind — mirrors the category/`dropdownOptions` validator pattern already established for TDM columns in Epic 1 Story 1.1
- [ ] Task 4 — CRUD endpoints (AC: 1)
  - [ ] Subtask 4.1 New `{backend}/app/api/endpoints/connectors.py`: `GET/POST/PUT/DELETE /api/v1/connectors`, following the exact thin-router + `_serialize()` pattern in `{backend}/app/api/endpoints/templates.py` (404/409 `HTTPException`, `select()` + `scalar_one_or_none()`); on create/update, encrypt `credentials` via Task 1's Fernet helper before persisting, and never include it in the response (`_serialize()` returns `ConnectorOut` shape only)
  - [ ] Subtask 4.2 Mount the new router in `{backend}/app/main.py` with prefix `/api/v1/connectors`
- [ ] Task 5 — MinIO/S3 connector implementation (AC: 2)
  - [ ] Subtask 5.1 New `{backend}/app/services/connectors/minio_s3_connector.py` (new `services/connectors/` package, since Epic 5 will likely add more connector kinds later even though only `minio_s3` is implemented now): a thin wrapper around the `minio` client (already a dependency, `>=7.2.5`, used today via `{backend}/app/services/storage.py::MinioService` for internal storage) — but this connector targets an **externally-configured** bucket/endpoint/credentials per connector row, not the platform's own fixed `MINIO_URL`/`MINIO_ACCESS_KEY` settings; do not reuse the existing `minio_service` singleton directly since it's hardcoded to the platform's own bucket — instantiate a fresh `Minio(...)` client per connector using its decrypted credentials
  - [ ] Subtask 5.2 **Input direction — "watches a configured bucket/prefix for new objects"**: this codebase's Celery worker runs with `worker_pool="solo"` and `worker_concurrency=1` (`{backend}/app/core/celery_app.py`) — a single-slot, non-forking worker. A long-running/blocking "watch" task would occupy that one slot indefinitely and block the actual detection pipeline chain from ever running concurrently. Combined with Epic 5's own "scheduling/cron triggers are out of scope" note, implement "watching" as an **on-demand list-and-diff check** (list objects in the bucket/prefix, compare against previously-seen object names/etags recorded per connector, return the new ones) invoked at pipeline-execution time (Story 5.2's "Run now"/API trigger) rather than a continuously polling background task — this reconciles the AC's "watches... for new objects" language with the actual worker capacity and the explicit no-scheduling constraint. Document this design choice clearly since "watches" could otherwise be misread as requiring a persistent poller.
  - [ ] Subtask 5.3 **Output direction**: write a given local file/buffer to the connector's configured bucket/prefix using the same per-connector `Minio` client, following `MinioService.upload_file()`'s method signature/style for consistency
  - [ ] Subtask 5.4 **"Test connection" action**: `POST /api/v1/connectors/{id}/test` (or a pre-save test against unsaved config, `POST /api/v1/connectors/test` with the full config+credentials in the body so users can verify before creating) — attempts `client.bucket_exists(bucket)` (or `list_objects` with a small limit) and returns `{"success": bool, "message": str}`; never let a connection failure raise a raw exception to the client — catch `S3Error`/`MaxRetryError`/connection errors and translate to a readable message, following the graceful-error-handling convention already used in `MinioService.__init__`
- [ ] Task 6 — `manual` pseudo-connector (AC: 3)
  - [ ] Subtask 6.1 The `manual` kind needs no real external I/O — it's a marker `Connector` row (`kind: "manual"`, empty/no credentials) that lets a Story 5.2 pipeline definition reference "the interactive upload path" as its input/output uniformly with real connectors. Ensure connector CRUD allows creating a `manual`-kind connector with no `config`/`credentials` at all (skip the per-kind validation from Task 3.2 for this kind), and that Story 5.2's execution logic special-cases `kind == "manual"` to mean "this pipeline is triggered by/produces output to the existing interactive wizard flow," not an automated fetch/write
- [ ] Task 7 — Deferred kinds registered but not implemented (AC: 4)
  - [ ] Subtask 7.1 Add `ftp_sftp`, `http`, `email` to the `kind` enum (Task 2.1) so the schema is forward-compatible, but any endpoint/service call that would need to actually connect via these kinds (e.g. "Test connection" on one of them) returns a clear `HTTPException(501, detail="'ftp_sftp' connector support is not yet implemented.")` — never a generic 500 or a silent no-op
- [ ] Task 8 — Frontend: Connector CRUD UI
  - [ ] Subtask 8.1 New page `{frontend}/app/(pages)/connectors/page.tsx` (list) and `[id]/page.tsx` (detail/edit), following the `templates/page.tsx` list-page pattern (local `useState` for list/loading/error, `useEffect` fetch-on-mount)
  - [ ] Subtask 8.2 Connector form: name, type, kind selector, kind-specific config fields (only `minio_s3` fields functional per this story; `ftp_sftp`/`http`/`email` shown as disabled/"coming soon" options in the kind selector, consistent with AC4); credentials fields are write-only inputs that never show a previously-saved value (show a "credentials configured ✓" indicator instead, backed by the `has_credentials` flag from Task 3.1)
  - [ ] Subtask 8.3 "Test connection" button wired to Task 5.4's endpoint, showing success/failure inline
  - [ ] Subtask 8.4 Add `listConnectors`, `getConnector`, `createConnector`, `updateConnector`, `deleteConnector`, `testConnector` to `{frontend}/lib/api.ts`, following existing naming/style
- [ ] Task 9 — Tests (AC: 5)
  - [ ] Subtask 9.1 `{backend}/tests/test_connectors.py`: credential encryption round-trip (encrypt → store → decrypt → original value, using a test Fernet key), per-kind config validation (accept valid `minio_s3` config, reject missing required fields, reject malformed config for `manual`), CRUD round trip asserting `credentials`/`encrypted_credentials` never appear in any response body, test-connection success (mocked MinIO client) and failure (mocked connection error → readable message, not a raw exception) paths

## Dev Notes

### Relevant Source Tree

- `{backend}/app/services/storage.py::MinioService` — the platform's **own** fixed-bucket MinIO client (`MINIO_URL`/`MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` from `Settings`, single bucket `"csv-datasets"`) — this is a different, unrelated concern from this story's per-connector external MinIO/S3 clients. Do not extend or repurpose `minio_service`; instantiate separate `Minio(...)` clients per connector using that connector's own decrypted credentials.
- `{backend}/app/api/endpoints/templates.py` — the CRUD reference pattern (thin router, `_serialize()`, 404/409 `HTTPException`) to copy for `connectors.py`.
- `{backend}/app/core/config.py` — add `CONNECTOR_ENCRYPTION_KEY` here, following the `GEMINI_API_KEY`/`MINIO_SECRET_KEY` precedent of secrets living in `Settings`/`.env`.
- `{backend}/app/core/celery_app.py` — `worker_pool="solo"`, `worker_concurrency=1` — a hard constraint on this story's "watch a bucket" design (Task 5.2); read this file before assuming a background poller is feasible.
- `{backend}/requirements.txt` — `cryptography>=42.0.0` already present (currently only a transitive dependency) and `minio>=7.2.5` — both reused here, no new dependencies needed for the `minio_s3` kind.
- Epic 1 Story 1.1's category/`dropdownOptions` Pydantic validator pattern — the precedent for this story's per-`kind` config validation.

### Patterns & Conventions

- **Backend architecture**: `services/connectors/` package (new), one module per kind, layered under `api/endpoints/connectors.py` — consistent with this codebase's `services/` business-logic layering.
- **Secrets never in `Settings`-adjacent JSON columns unencrypted**: this is a new pattern for this codebase (no prior encrypted-column precedent exists) — be deliberate and explicit about the encrypt-before-persist / never-decrypt-in-a-response boundary, since getting this wrong (e.g. accidentally including `encrypted_credentials` in a serialized response) would be a real credential leak, not just a bug.
- **Error handling**: `HTTPException(404, ...)` missing connector; `HTTPException(422, ...)` per-kind config validation failures (via Pydantic validators, consistent with Epic 1's TDM validator style); `HTTPException(501, ...)` for the deferred kinds (Task 7); test-connection failures return a `200` with `{"success": false, "message": ...}` rather than an HTTP error, since "the test failed" is an expected, valid outcome, not a server error — consistent with how this codebase treats expected-failure states (e.g. `fallback_mode` flags) as normal response data rather than exceptions.
- **API response format**: no global envelope; flat CRUD objects, consistent with `templates.py`'s `_serialize()` shape.
- **Frontend**: feature-based page under `app/(pages)/connectors/`, no global store, `templates/page.tsx`'s list/loading/error local-state pattern, native controlled inputs for the connector form.

### Tech Stack

- **Backend**: FastAPI >=0.110.0, async SQLAlchemy >=2.0.29, MySQL 8.0.35, Alembic >=1.13.1 (chain-repair prerequisite as always).
- **Encryption**: `cryptography>=42.0.0` (`Fernet`), already a dependency.
- **Object Storage**: `minio>=7.2.5` client, already a dependency, reused for per-connector clients distinct from the platform's own `minio_service`.
- **Testing**: pytest/pytest-mock/httpx, following `test_upload.py`'s established mocking conventions (`conftest.py` stubs `minio`, `sqlalchemy`, etc. — this story's tests should mock the per-connector `Minio` client the same way `mocker.patch("app.api.endpoints.upload.minio_service...")` mocks the existing one).

### Notes from Previous Stories

- This story has no direct code dependency on Epics 1–4's TDM/mapping/cleaning work, but Epic 5's Dependencies section requires Epic 1 and Epic 4 to be **complete** before this epic starts, since Story 5.2 (next) composes connectors with TDMs and the confirm-gate/canonical-Parquet machinery those epics built.
- The Alembic chain-repair prerequisite from Epic 1 Story 1.1 applies here too, as it has to every migration-adding story so far in this initiative.

### Testing

- Test file location: `{backend}/tests/test_connectors.py` (new).
- Framework: pytest + pytest-mock + httpx `AsyncClient`, per established conventions; mock the per-connector `Minio` client for test-connection success/failure paths — never hit a real external MinIO/S3 endpoint in tests.
- Test types required: encryption round-trip, per-kind config validation (accept/reject), CRUD-never-leaks-credentials assertion (explicitly check response JSON does not contain `credentials`/`encrypted_credentials` keys), test-connection success/failure.
