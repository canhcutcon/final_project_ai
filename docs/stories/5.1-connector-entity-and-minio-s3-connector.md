# Story 5.1: Connector entity & MinIO/S3 connector

## Status

Review

## Story

**As a** platform operator,
**I want** to register input/output connectors,
**so that** pipelines can receive and deliver data without manual uploads.

## Acceptance Criteria

1: `connectors` table + CRUD API/UI: name, `type: input | output`, `kind: manual | minio_s3 | ftp_sftp | http | email`, and kind-specific config; credentials are encrypted at rest and never returned by the API (write-only fields)
2: MinIO/S3 implemented first for both directions: input watches a configured bucket/prefix for new objects; output writes result files to a bucket/prefix; a "Test connection" action verifies credentials and access before saving
3: The `manual` kind wraps the interactive upload path as a pseudo-connector so a pipeline definition can start from manual uploads uniformly
4: `ftp_sftp`, `http`, `email` kinds are registered as enum values with clear "not yet implemented" responses (schema-ready, implementation deferred)
5: Unit tests: credential encryption round-trip, config validation per kind, test-connection success/failure paths

- [x] Task 5 — MinIO/S3 connector implementation (AC: 2)
  - [x] Subtask 5.1 New `{backend}/app/services/connectors/minio_s3_connector.py` (new `services/connectors/` package, since Epic 5 will likely add more connector kinds later even though only `minio_s3` is implemented now): a thin wrapper around the `minio` client (already a dependency, `>=7.2.5`, used today via `{backend}/app/services/storage.py::MinioService` for internal storage) — but this connector targets an **externally-configured** bucket/endpoint/credentials per connector row, not the platform's own fixed `MINIO_URL`/`MINIO_ACCESS_KEY` settings; do not reuse the existing `minio_service` singleton directly since it's hardcoded to the platform's own bucket — instantiate a fresh `Minio(...)` client per connector using its decrypted credentials
  - [x] Subtask 5.2 **Input direction — "watches a configured bucket/prefix for new objects"**: this codebase's Celery worker runs with `worker_pool="solo"` and `worker_concurrency=1` (`{backend}/app/core/celery_app.py`) — a single-slot, non-forking worker. A long-running/blocking "watch" task would occupy that one slot indefinitely and block the actual detection pipeline chain from ever running concurrently. Combined with Epic 5's own "scheduling/cron triggers are out of scope" note, implement "watching" as an **on-demand list-and-diff check** (list objects in the bucket/prefix, compare against previously-seen object names/etags recorded per connector, return the new ones) invoked at pipeline-execution time (Story 5.2's "Run now"/API trigger) rather than a continuously polling background task — this reconciles the AC's "watches... for new objects" language with the actual worker capacity and the explicit no-scheduling constraint. Document this design choice clearly since "watches" could otherwise be misread as requiring a persistent poller.
  - [x] Subtask 5.3 **Output direction**: write a given local file/buffer to the connector's configured bucket/prefix using the same per-connector `Minio` client, following `MinioService.upload_file()`'s method signature/style for consistency
  - [x] Subtask 5.4 **"Test connection" action**: `POST /api/v1/connectors/{id}/test` (or a pre-save test against unsaved config, `POST /api/v1/connectors/test` with the full config+credentials in the body so users can verify before creating) — attempts `client.bucket_exists(bucket)` (or `list_objects` with a small limit) and returns `{"success": bool, "message": str}`; never let a connection failure raise a raw exception to the client — catch `S3Error`/`MaxRetryError`/connection errors and translate to a readable message, following the graceful-error-handling convention already used in `MinioService.__init__`
- [x] Task 6 — `manual` pseudo-connector (AC: 3)

Ensure connector CRUD allows creating a `manual`-kind connector with no `config`/`credentials` at all (skip the per-kind validation from Task 3.2 for this kind), and that Story 5.2's execution logic special-cases `kind == "manual"` to mean "this pipeline is triggered by/produces output to the existing interactive wizard flow," not an automated fetch/write

## Dev Notes

### Relevant Source Tree

- `{backend}/app/services/storage.py::MinioService` — the platform's **own** fixed-bucket MinIO client (`MINIO_URL`/`MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` from `Settings`, single bucket `"csv-datasets"`) — this is a different, unrelated concern from this story's per-connector external MinIO/S3 clients. Do not extend or repurpose `minio_service`; instantiate separate `Minio(...)` clients per connector using that connector's own decrypted credentials.
- `{backend}/app/api/endpoints/templates.py` — the CRUD reference pattern (thin router, `_serialize()`, 404/409 `HTTPException`) to copy for `connectors.py`.
- `{backend}/app/core/config.py` — add `CONNECTOR_ENCRYPTION_KEY` here, following the `GEMINI_API_KEY`/`MINIO_SECRET_KEY` precedent of secrets living in `Settings`/`.env`.
- `{backend}/app/core/celery_app.py` — `worker_pool="solo"`, `worker_concurrency=1` — a hard constraint on this story's "watch a bucket" design (Task 5.2); read this file before assuming a background poller is feasible.
- `{backend}/requirements.txt` — `cryptography>=42.0.0` already present (currently only a transitive dependency) and `minio>=7.2.5` — both reused here, no new dependencies needed for the `minio_s3` kind.
- Epic 1 Story 1.1's category/`dropdownOptions` Pydantic validator pattern — the precedent for this story's per-`kind` config validation.

### Patterns & Conventions

- **Backend architecture**: `services/connectors/` package (new), one module per kind, layered under `api/endpoints/connectors.py` — consistent with this codebase's `services/` business-logic layering.
- **Secrets never in `Settings`-adjacent JSON columns unencrypted**: this is a new pattern for this codebase (no prior encrypted-column precedent exists) — be deliberate and explicit about the encrypt-before-persist / never-decrypt-in-a-response boundary, since getting this wrong (e.g. accidentally including `encrypted_credentials` in a serialized response) would be a real credential leak, not just a bug.
- **Error handling**: `HTTPException(404, ...)` missing connector; `HTTPException(422, ...)` per-kind config validation failures (via Pydantic validators, consistent with Epic 1's TDM validator style); `HTTPException(501, ...)` for the deferred kinds (Task 7); test-connection failures return a `200` with `{"success": false, "message": ...}` rather than an HTTP error, since "the test failed" is an expected, valid outcome, not a server error — consistent with how this codebase treats expected-failure states (e.g. `fallback_mode` flags) as normal response data rather than exceptions.
- **API response format**: no global envelope; flat CRUD objects, consistent with `templates.py`'s `_serialize()` shape.
- **Frontend**: feature-based page under `app/(pages)/connectors/`, no global store, `templates/page.tsx`'s list/loading/error local-state pattern, native controlled inputs for the connector form.

### Tech Stack

- **Backend**: FastAPI >=0.110.0, async SQLAlchemy >=2.0.29, MySQL 8.0.35, Alembic >=1.13.1 (chain-repair prerequisite as always).
- **Encryption**: `cryptography>=42.0.0` (`Fernet`), already a dependency.
- **Object Storage**: `minio>=7.2.5` client, already a dependency, reused for per-connector clients distinct from the platform's own `minio_service`.
- **Testing**: pytest/pytest-mock/httpx, following `test_upload.py`'s established mocking conventions (`conftest.py` stubs `minio`, `sqlalchemy`, etc. — this story's tests should mock the per-connector `Minio` client the same way `mocker.patch("app.api.endpoints.upload.minio_service...")` mocks the existing one).
