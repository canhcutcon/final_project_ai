# Story 3.3: AI Prompts with preview diff

## Status

Approved

## Story

**As a** data operator,
**I want** to describe a bulk edit in natural language and preview it before applying,
**so that** complex transforms don't require exports to Excel.

## Acceptance Criteria

1: A Prompts input at the Review stage sends the instruction plus TDM schema (headers only, no full data) to the LLM, which returns a transform executed against the working data copy in a sandboxed executor — no I/O, no imports, whitelisted pandas-style operations only
2: The result renders as a preview diff: affected-row count and a before/after sample (≥ 10 rows or all affected if fewer); nothing is applied without explicit approval
3: Applied prompts are logged in `transform_log` with prompt text, the generated transform, and affected-row count; undo restores the pre-prompt state exactly
4: Failure modes are handled gracefully: an un-executable or rejected transform returns a readable error (not a stack trace); a transform affecting zero rows shows a warning instead of a silent no-op
5: The feature is hidden when the AI-disabled flag is set

## ⚠️ Security note (read before implementing)

This story is explicitly flagged in the Epic 3 "Additional Notes" as **the highest-risk component in this PRD** (LLM-generated code, executed server-side) and **requires a security review before merge**, independent of normal code review. Nothing in this story should be implemented and merged without that review actually happening. The design direction below (structured whitelist, not raw code execution) is a recommendation to make that review tractable — it does not replace the review.

## Tasks / Subtasks

- [ ] Task 1 — Executor design decision (AC: 1) — **do this before writing any executor code**
  - [ ] Subtask 1.1 **No sandboxing library or precedent exists anywhere in this codebase today** (verified: no `RestrictedPython`, no existing `exec`/`eval` usage, nothing in `{backend}/requirements.txt`). This is genuinely greenfield. Recommended design: do **not** have the LLM emit executable Python text and `exec()`/`eval()` it, even inside a restricted-globals sandbox — AST-based Python sandboxes (including `RestrictedPython`) have a long history of escapes, and "no imports" is very hard to guarantee against a determined or confused-LLM-generated payload. Instead, have the LLM emit a **structured JSON operation plan** from a fixed, closed whitelist (e.g. `{"op": "strip_whitespace", "column": "..."}`, `{"op": "replace_pattern", "column": "...", "pattern": "...", "replacement": "..."}`, `{"op": "split_column", ...}`, `{"op": "filter_and_set", "condition": {...}, "column": "...", "value": "..."}`), and have the backend interpret that JSON with real, hand-written pandas calls — never executing LLM-authored code text directly. This turns "sandbox arbitrary code" into "validate a JSON payload against a schema," which is a much smaller and more auditable attack surface, matching AC1's own wording ("whitelisted pandas-style operations only").
  - [ ] Subtask 1.2 Define the initial operation whitelist as a small, explicit set covering the transforms this PRD actually needs (string ops: strip/replace/regex-replace/case; column ops: split/merge/rename within the TDM's existing columns; row ops: filter-and-set with a comparison condition) — keep it deliberately small at launch; expanding the whitelist later is cheap, narrowing it after the fact (once users depend on an op) is not
  - [ ] Subtask 1.3 Get the design (Subtask 1.1/1.2) reviewed by whoever owns security review for this project **before** building Task 2 — this is not optional per the epic's explicit note
- [ ] Task 2 — Prompt → operation-plan generation (AC: 1)
  - [ ] Subtask 2.1 New module `{backend}/app/services/prompt_executor_service.py`: build a prompt sending the user's instruction + **TDM schema headers only** (`key, label, columnType` — never sample data or full rows, per AC1 and NFR1) to Gemini via the same dual-provider pattern as `gemini_fix_service.py` (Gemini primary, Ollama fallback), requesting a JSON response matching the whitelist schema from Task 1.2
  - [ ] Subtask 2.2 Validate the LLM's JSON response strictly against the whitelist schema (e.g. Pydantic models per operation type with a discriminated union on `op`) before ever touching real data — any operation not in the whitelist, or any malformed payload, is rejected before execution, not caught mid-execution
- [ ] Task 3 — Sandboxed interpreter for whitelisted ops (AC: 1)
  - [ ] Subtask 3.1 Implement one hand-written pandas function per whitelisted operation (from Task 1.2) in `prompt_executor_service.py` — each function takes the working `DataFrame` copy + validated operation parameters and returns a new `DataFrame`; no `exec`/`eval`/`importlib`/`open`/network calls anywhere in this code path
  - [ ] Subtask 3.2 Enforce a hard execution time cap (e.g. via a timeout wrapper around the interpreter call) per the epic's "execution time capped" requirement, and operate only on an in-memory copy of the working data — never the persisted original — so a bad transform can't corrupt source data
  - [ ] Subtask 3.3 Never operate on numeric columns already flagged by Story 3.2's outlier-exclusion gate as containing outliers, unless the operation plan explicitly targets a different column — reuse Story 3.2's outlier check as a guard before applying row-mutating operations, consistent with the epic's "anomaly signal is never altered" objective
- [ ] Task 4 — Preview endpoint (AC: 2, 4)
  - [ ] Subtask 4.1 Add `POST /api/v1/datasets/{id}/prompts/preview` (body: `{instruction: str}`) to a new `{backend}/app/api/endpoints/prompts.py`: runs Task 2's generation + Task 3's interpreter against the working copy, and returns `{operation_plan, affected_row_count, before_after_sample}` — sample is the first 10 affected rows (or all of them if fewer, per AC2) as `{before: {...}, after: {...}}` pairs — **without persisting anything**
  - [ ] Subtask 4.2 If `affected_row_count == 0`, return a distinct response shape/flag (e.g. `{"warning": "This transform did not match any rows."}`) rather than an empty-but-technically-successful preview, so the frontend can render a warning instead of silently showing nothing (AC4)
  - [ ] Subtask 4.3 If the LLM's operation plan fails validation (Task 2.2) or the interpreter raises during a dry-run preview, return `HTTPException(400, detail="<readable message>")` — e.g. "Could not understand that instruction — try rephrasing it more specifically" for invalid plans, or a specific message for a caught interpreter error — **never** let a raw Python traceback/stack trace reach the response (AC4)
- [ ] Task 5 — Confirm/apply endpoint (AC: 2, 3)
  - [ ] Subtask 5.1 Add `POST /api/v1/datasets/{id}/prompts/apply` (body: `{instruction: str, operation_plan: {...}}` — the client re-submits the exact plan it previewed, so apply never re-generates from the LLM and can't drift from what the user actually approved) that re-runs Task 3's interpreter, writes the result to the working data copy, and persists **one `TransformLog` entry per prompt application** (not per row) capturing `prompt text`, the `operation_plan` JSON (as the "generated transform" AC3 requires), and `affected_row_count`
  - [ ] Subtask 5.2 Nothing is applied without this explicit second call — the preview endpoint (Task 4) must never mutate persisted state, only the apply endpoint does (AC2 "nothing is applied without explicit approval")
- [ ] Task 6 — Undo integration (AC: 3)
  - [ ] Subtask 6.1 Coordinate with Story 3.4's undo/redo mechanism: a prompt application must be undoable as a single unit (restoring every row it touched to its pre-prompt values), not row-by-row — ensure the `TransformLog` entry from Task 5.1 carries enough information (either the full before-state for affected rows, or a reference the undo mechanism can use to recompute it) for Story 3.4 to implement exact restoration; do not finalize this story's `TransformLog` schema without checking Story 3.4's undo design for what it needs
- [ ] Task 7 — AI-disabled visibility (AC: 5)
  - [ ] Subtask 7.1 Hide the Prompts input entirely in the frontend when the AI-disabled flag (`AI_MAPPING_ENABLED`, Epic 1 Story 1.3) is set, and have the preview/apply endpoints return `HTTPException(403, detail="AI features are disabled for this deployment.")` as a defense-in-depth backend check (don't rely on the frontend hiding it alone, since the endpoint is directly callable)
  - [ ] Subtask 7.2 **Scope note vs. the `ai_enabled` per-call parameter (Stories 1.3/3.2):** unlike `suggest_mapping`/LLM-fixer, the Prompts feature is a **user-typed, interactive-only** action — Story 5.2's unattended pipelines explicitly never invoke it (they run deterministic cleaning with "no Prompts" per 5.2 Task 3.1). So this endpoint reads the **global** `AI_MAPPING_ENABLED` directly and does **not** take an `ai_enabled` parameter; there is no per-pipeline caller to override it. Document this asymmetry so a later refactor doesn't "helpfully" thread a param through here that nothing will ever pass.
- [ ] Task 8 — Frontend: Prompts input + diff preview
  - [ ] Subtask 8.1 Add a Prompts text input at the Review stage (wherever Epic 4's Review Entries grid lands, or an interim location if that doesn't exist yet at implementation time) with a "Preview" action calling the new preview endpoint
  - [ ] Subtask 8.2 Render the before/after sample as a simple diff table (old value struck through or highlighted next to the new value, per row) plus the affected-row count; show the zero-affected-rows warning state distinctly from a normal preview
  - [ ] Subtask 8.3 "Apply" button calls the apply endpoint with the previewed plan; readable error messages (Task 4.3/7.1) surface inline, never as a raw error dump
  - [ ] Subtask 8.4 Add `previewPrompt(datasetId, instruction)` and `applyPrompt(datasetId, instruction, plan)` to `{frontend}/lib/api.ts`
- [ ] Task 9 — Tests (security-relevant — do not skip)
  - [ ] Subtask 9.1 `{backend}/tests/test_prompt_executor.py`: whitelist validation rejects any operation not in the schema; a plan referencing a non-existent column is rejected with a readable error, not a crash; execution-time cap actually terminates a deliberately slow operation in tests (e.g. simulate via a monkeypatched slow op) rather than only asserting the cap exists in code; zero-affected-rows returns the warning shape, not a silent success
  - [ ] Subtask 9.2 Explicit **negative security tests**: attempt to smuggle an out-of-whitelist operation, a plan that references a filesystem path or network-like string, and confirm each is rejected before any pandas execution occurs — these tests exist specifically to be exercised by the mandatory security review, not just as ordinary unit tests
  - [ ] Subtask 9.3 Integration test: preview → apply → `transform_log` entry with correct prompt/plan/affected-row-count → (coordinate with Story 3.4) undo restores exact pre-prompt state

## Dev Notes

### Relevant Source Tree

- `{backend}/app/services/gemini_fix_service.py` — dual-provider (Gemini → Ollama → fallback) pattern to reuse for prompt-to-operation-plan generation; note this story needs **strict JSON-schema validation** on top of the existing defensive parsing, since the LLM output here drives code execution rather than just a suggested value.
- No existing sandboxing/restricted-execution code anywhere in `{backend}` or `{ai_services_detection}` — this story introduces the concept from scratch; there is nothing to extend, only new code to write carefully.
- Story 3.1's `import_issues` / Story 3.2's `cleaning_service.py` and outlier-exclusion gate — this story's interpreter should respect the same "never alter flagged-outlier numeric values" rule Story 3.2 establishes.
- `{backend}/app/models/data_fix_log.py` / `review_queue.py` — modeling-style precedent (indexing, enum-based `source`/`status` columns) for the new `TransformLog` model shared with Stories 3.2/3.4.
- Epic 1 Story 1.1's Alembic chain repair — prerequisite for the `transform_log` migration (shared with Story 3.2, do not create a second competing migration for the same table).

### Patterns & Conventions

- **Backend architecture**: new `prompt_executor_service.py`, layered the same as other `services/` modules; the endpoint (`prompts.py`) stays thin — preview/apply orchestration only, no interpreter logic inline in the router.
- **Security-by-construction over sandboxing**: this codebase has no precedent for executing dynamic/generated code, and no dependency for it either — the safest path consistent with "whitelisted pandas-style operations only" (AC1's own wording) is a structured-operation interpreter, not a code sandbox. Treat "add a new whitelisted op" as a deliberate, reviewed code change, never a runtime-configurable thing.
- **Graceful degradation / hidden-when-disabled**: matches the AI-disabled pattern established in Epic 1 Story 1.3 (`AI_MAPPING_ENABLED`) and reused in Story 3.2 — same flag, same "hidden in UI + defense-in-depth check in the endpoint" approach.
- **Error handling**: `HTTPException(400, ...)` for invalid/rejected plans and un-executable transforms with a **readable message**, never a raw traceback (AC4 is explicit about this); `HTTPException(403, ...)` when AI is disabled; `HTTPException(404, ...)` for missing dataset.
- **NFR1 data minimization**: only TDM schema headers (not data) go to the LLM for plan generation — stricter than Story 3.2's "error cells + minimal context," since this path sends no row data at all.
- **API response format**: no global envelope; preview/apply return flat objects (`operation_plan`, `affected_row_count`, `before_after_sample` / `warning`).

### Tech Stack

- **LLM — External API**: `google-generativeai` (`gemini-2.5-flash-lite`) primary, local Ollama (`qwen2.5:3b-instruct`) fallback, same as elsewhere in this epic.
- **Data Processing**: pandas for every whitelisted operation's actual implementation.
- **No new sandboxing dependency planned** — the structured-whitelist approach avoids needing `RestrictedPython` or similar; if the security review concludes a code-sandboxing library is required instead, that changes this story's dependencies significantly and should be re-scoped, not silently added.
- **Testing**: pytest/pytest-mock, mocking the LLM call; the negative security tests (Task 9.2) are pure Python (no external calls) and should run in every CI/local run.

### Notes from Previous Stories

- Story 3.1 provides `import_issues`; Story 3.2 provides `cleaning_service.py`'s outlier-exclusion gate (reused here, Task 3.3) and is the other writer of the shared `transform_log` table — coordinate the migration so it's added once, not twice.
- Story 3.2's `AI_MAPPING_ENABLED` reuse pattern (Epic 1 Story 1.3) is reused again here for AC5.
- Story 3.4 (next) implements undo/redo across all mutation kinds including this story's prompt applications — this story's `TransformLog` schema must carry what Story 3.4 needs for exact restoration (Task 6.1); check Story 3.4's design before finalizing the schema, or expect a follow-up migration if the two land out of order.

### Testing

- Test file location: `{backend}/tests/test_prompt_executor.py` (new), alongside `test_cleaning_service.py` (Story 3.2).
- Framework: pytest + pytest-mock, mocking the LLM call — never call real Gemini/Ollama in tests.
- Test types required: whitelist-schema validation tests, readable-error-on-failure tests, zero-affected-rows warning test, explicit negative security tests (Task 9.2) proving out-of-whitelist/malformed plans are rejected pre-execution, and a full preview→apply→log(→undo, coordinating with Story 3.4) integration test.
- This story's test suite is part of what the mandatory security review will look at — write the negative tests to be legible to a reviewer who hasn't read the implementation, not just to satisfy coverage.
