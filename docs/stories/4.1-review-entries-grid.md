# Story 4.1: Review Entries grid

## Status

Approved

## Story

**As a** data operator,
**I want** an Excel-like grid over the mapped, cleaned data,
**so that** I can make final edits and verify the import.

## Acceptance Criteria

1: The Review Entries stage renders TDM columns with required-column markers (starred/highlighted); cells with open issues are highlighted with tooltip messages from `import_issues`
2: Grid tooling: total error count, "Find error" navigation (jump to next error cell), row filter (all / rows-with-errors / valid), column sort, find & replace, undo/redo wired to the Epic 3 session mechanism
3: Cell edits re-validate only the affected cells inline (Story 3.1 AC5) and update the error count without a full-grid refresh
4: Performance within NFR3 on 50k rows via virtualized rendering (only visible rows mounted); grid edits reflect in < 200 ms with server round-trips async
5: `category` columns edit via dropdown of TDM options; `date` columns display in the TDM `outputFormat`

  - [ ] Subtask 1.1 `{frontend}/package.json` currently has **only** `next` (14.2.35), `react`/`react-dom` (^18) as dependencies — there is no grid, table, or virtualization library of any kind (no `react-window`, `@tanstack/react-virtual`, `@tanstack/react-table`, `ag-grid`, `handsontable`). Epic 4's own note ("evaluate existing dependencies before adding a new library") has nothing to evaluate — a new dependency is required to meet AC4's "only visible rows mounted" requirement. Recommend `@tanstack/react-virtual` (headless, small, pairs naturally with a hand-rolled `<table>`/div-grid matching this codebase's existing plain-Tailwind-table style in `SchemaMappingStep.tsx`, `templates/page.tsx`) over a full grid framework like `ag-grid`/`handsontable`, which would impose their own styling system and be a much heavier addition against this app's minimal-dependency pattern. Confirm this choice with whoever reviews frontend dependency additions before starting Task 3.
- [ ] Task 2 — Grid data endpoint (AC: 1)
  - [ ] Subtask 2.1 Add `GET /api/v1/datasets/{id}/grid` (new `{backend}/app/api/endpoints/grid.py`, or extend `datasets.py`) returning the mapped, TDM-keyed data as paginated/chunked rows (support `offset`/`limit` query params for virtualized fetch-on-scroll, e.g. `Query(default=200, ge=1, le=1000)` per this codebase's existing pagination style) — each row keyed by TDM `key`, plus the TDM column definitions (`key, label, columnType, outputFormat, dropdownOptions, validations.required`) so the frontend can render required-markers and per-column edit widgets without a second round trip
  - [ ] Subtask 2.2 Include per-cell issue references: either embed `{value, issue: {issue_type, message} | null}` per cell in the row payload, or return `import_issues` for the current row/column window alongside the raw values — pick whichever keeps payload size reasonable at 50k-row scale (embedding per-cell issue objects for every one of 50k×N cells could bloat the payload; consider returning issues only for the currently-fetched row window, matching the virtualized fetch pattern)
  - [ ] Subtask 2.3 404 if dataset not found; this endpoint reads from the working data copy established in Epic 3 (post-cleaning state), not the raw upload
  - [ ] Subtask 2.4 **This story owns setting `import_status = "reviewed"`** (per the setter-ownership assignment documented in Story 4.2's `dataset.py` note). Transition `dataset.import_status` from `cleaning` → `reviewed` when the Review Entries stage is entered (e.g. on first authenticated load of this grid endpoint for a `cleaning`-state dataset), if not already at or past that stage — so Story 4.2's pre-pipeline stage-progress display shows a real, settable `reviewed` step rather than an aspirational one.

  - [ ] Subtask 3.3 `category` columns render as a `<select>` of the TDM column's `dropdownOptions` when editing (AC5); `date` columns display formatted per the TDM column's `outputFormat` (parse the stored value and format for display, independent of the underlying stored representation)
  - [ ] Subtask 3.4 Cell editing follows the existing controlled-input convention (no form library in this codebase) — inline edit on click/focus, commit on blur/enter
- [ ] Task 4 — Grid tooling (AC: 2)
  - [ ] Subtask 4.1 Total error count: derived from Story 3.1's issue-summary endpoint (`GET /api/v1/datasets/{id}/issues/summary`) rather than counting client-side over a partially-loaded virtualized dataset
  - [ ] Subtask 4.2 "Find error" navigation: request the next error cell's row/column from the backend (extend the issues-summary endpoint or add a small `GET /api/v1/datasets/{id}/issues/next?after_row=...` helper) and scroll the virtualized grid to that position — avoid relying on client-side knowledge of the full issue list at 50k-row scale
  - [ ] Subtask 4.3 Row filter (all / rows-with-errors / valid): pass as a filter parameter to the grid data endpoint (Task 2.1) so filtering happens server-side, not by filtering an already-fetched full dataset
  - [ ] Subtask 4.4 Column sort: also server-side via a `sort_by`/`sort_dir` param on the grid data endpoint, for the same 50k-row performance reason
  - [ ] Subtask 4.5 Find & replace: a scoped bulk-edit action (target column + search value + replace value) — reuse Story 3.2's apply-per-column mechanism/`TransformLog` pattern rather than inventing a parallel bulk-write path, since both are "apply the same value-level change to many cells and log it". **Write every affected cell's `TransformLog` row with a shared `operation_group` id (the column from Story 3.2's canonical schema) so Story 3.4's undo/redo reverts the whole find-&-replace as one atomic unit, not cell-by-cell.**
  - [ ] Subtask 4.6 Undo/redo: wire the grid's Undo/Redo buttons directly to Story 3.4's `POST /api/v1/datasets/{id}/undo` / `/redo` endpoints and `getDatasetLineage` — this story does not implement a second undo mechanism

  - [ ] Subtask 5.3 This endpoint is the dependency Epic 3 Story 3.4's test simulated manually (it wrote directly to `transform_log` in test setup since no endpoint existed yet). ## Dev Notes

### Relevant Source Tree

- `{frontend}/package.json` — **no virtualization/grid dependency exists today**; this story adds one (Task 1).
- `{frontend}/components/upload/SchemaMappingStep.tsx`, `{frontend}/app/(pages)/templates/page.tsx` — existing plain-`<table>` + Tailwind styling convention to match visually, even though the new grid needs virtualization under the hood.
- Story 3.1's `import_issues` table and targeted re-validation, Story 3.1's `GET /api/v1/datasets/{id}/issues/summary` — direct inputs to this story's error highlighting, count, and "Find error" navigation.
- Story 3.2's per-column apply mechanism and `TransformLog` — the pattern to reuse for Find & Replace (Task 4.5) rather than a new bulk-write path.
- Story 3.4's undo/redo endpoints (`POST /api/v1/datasets/{id}/undo`/`redo`) and lineage timeline — wired directly into this grid's tooling (Task 4.6), not reimplemented.
- Story 3.4's `TransformLog` schema, designed with a `source: "manual"` value reserved but unproduced until now — **this story is that producer** (Task 5.1).
- Epic 1's TDM schema (`key, label, columnType, outputFormat, dropdownOptions, validations`) — the column definitions this grid renders.

### Patterns & Conventions

- **Backend architecture**: new `grid.py` endpoint module (or extend `datasets.py`), thin router, business logic (pagination/filter/sort over the working data copy) in a `services/` module if it grows non-trivial.
- **Server-side heavy lifting for scale**: consistent with NFR3's explicit framing ("grid edits reflected < 200 ms (server round-trips async)") — filtering, sorting, and "find next error" are backend responsibilities, not client-side operations over a fully-loaded 50k-row array; this matches how Story 3.1's targeted re-validation and Story 3.2's bulk-apply were also designed for scale.
- **Frontend component structure**: feature-based, under a new `components/review/` folder — consistent with existing `components/anomaly/`, `components/upload/` organization.
- **Frontend state management**: no global store; grid state (loaded row window, filter, sort, selection) lives in local component state in `ReviewEntriesGrid.tsx`, per this codebase's established convention.
- **No form library**: category dropdowns and inline cell editors use native controlled `<select>`/`<input>` elements, consistent with the rest of the app.
- **Error handling**: `HTTPException(404, ...)` for missing dataset; `HTTPException(422, ...)` for an edit targeting an invalid column/row; `HTTPException(500, ...)` after `logger.exception(...)` for unexpected failures.
- **API response format**: no global envelope; grid data is a flat paginated object (`{rows, total_count, columns}`), cell-edit response is a small flat object.

### Tech Stack

- **Frontend**: Next.js 14.2.35, React 18, TypeScript ^5, Tailwind CSS — plus the new virtualization dependency from Task 1 (recommend `@tanstack/react-virtual` given the "evaluate existing deps first" note found nothing to reuse).
- **Backend**: FastAPI >=0.110.0, async SQLAlchemy for the grid data endpoint; pandas for reading/writing the working data copy (Parquet, consistent with this codebase's existing Parquet-for-intermediate-storage convention seen in `pipeline_tasks.py`/`agent_fix_task.py`).
- **Testing**: pytest/httpx (backend), Jest + Testing Library (frontend) — no e2e/visual-regression tooling exists in this project, so performance/virtualization verification (Task 6.2) is manual, not automated.

### Notes from Previous Stories

- Epic 3 Story 3.1 provides `import_issues` + targeted re-validation; Story 3.2 provides the per-column bulk-apply pattern this story's Find & Replace reuses; Story 3.4 provides undo/redo/lineage endpoints this story's grid tooling wires into directly, and reserved (but didn't implement) the `source: "manual"` `TransformLog` value that this story's `PATCH /cell` endpoint is the first to actually write.
- Epic 1/Epic 2 determine the TDM columns and structure-resolved data this grid renders over — by the time this story runs, the dataset should be past `import_status = "mapped"`/cleaning stages from Epic 3.
- This story is explicitly called out in Epic 4's own Dependencies as requiring "Epics 1–3 complete" — do not start implementation against a codebase where those stories haven't landed, since the grid endpoint depends on `import_issues`, `dataset_mappings`, and the TDM schema all existing.

### Testing

- Test file location: `{backend}/tests/test_grid.py` (new); frontend tests alongside `{frontend}/__tests__/`.
- Framework: pytest + httpx (backend, following `AsyncClient` + `dependency_overrides` conventions); Jest + React Testing Library + jsdom (frontend, per `jest.config.ts`).
- Test types required: backend pagination/filter/sort/manual-edit/re-validation correctness; frontend rendering correctness for required markers, issue highlights + tooltips, category/date cell editing. No automated performance/virtualization test exists in this codebase's conventions — treat AC4's performance requirement as a manual verification step during implementation, documented in the PR rather than asserted in CI.
