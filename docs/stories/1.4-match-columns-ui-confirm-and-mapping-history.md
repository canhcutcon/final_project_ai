# Story 1.4: Match Columns UI + confirm + mapping history

## Status

Draft

## Story

**As a** data operator,
**I want** to review, adjust, and confirm the proposed mapping,
**so that** the import proceeds with a mapping I trust — and repeats automatically next time.

## Acceptance Criteria

1: Match Columns wizard stage renders each source column with: a "Select or add column…" dropdown of TDM targets, the suggestion pre-selected with confidence badge and layer label, a data-quality readout (% rows with a value) and up to 3 sample values, and a visible flag on unmatched columns
2: "Create new column" in the dropdown opens an inline TDM-column creator (key/label/type) and appends it to the TDM on confirm
3: `POST /api/v1/datasets/{id}/mapping/confirm` persists the final mapping to `dataset_mappings` and upserts `mapping_history` keyed by header signature (ordered normalized source headers hashed per TDM); dataset `import_status` advances to `mapped`
4: Re-uploading a file with an identical header signature auto-maps at confidence 1.0 via the historical layer and the stage shows "auto-matched — review optional" instead of requiring per-column action
5: For `category` targets, source-value → dropdown-option assignments made by the user are captured at confirm and remembered in mapping history for the next import

## Dev Notes

### Relevant Source Tree

- `{frontend}/components/upload/SchemaMappingStep.tsx` — **the component this story reworks**. Today it does purely client-side type inference (`inferType()` on the first 3 sample values) and an optional client-side "Load Template" merge (`applyTemplate`) with a `matchSummary` badge (`X/Y columns matched from template`) — no backend call exists yet for mapping suggestions. This story replaces that local heuristic with the real `suggestMapping()`/`confirmMapping()` backend calls from Stories 1.3/1.1, while preserving the existing visual structure (source-header/sample-values column on the left, target-mapping form on the right) and the legacy-template-compatible affordance.
- `{frontend}/types/upload.ts` — existing `ColumnConfig`, `DataType`, `Template` types; extend with `MappingProposal` and TDM-aware config shape.
- `{frontend}/components/upload/WizardStepper.tsx` — overall wizard step sequencing that hosts this stage.
- `{backend}/app/services/mapping_service.py` (Story 1.3) — provides `suggest_mapping()` and the shared `compute_header_signature()` helper; **reuse it directly** for the confirm endpoint's `mapping_history` upsert key rather than recomputing signatures ad hoc.
- `{backend}/app/models/dataset.py` — `import_status` field (added in Story 1.1) advances to `"mapped"` here.
- Epic 1 file, "Additional Notes": header-signature logic must be shared code across Stories 1.3/1.4 and Epic 5 — do not duplicate.

### Patterns & Conventions

- **Component structure**: keep the Match Columns stage as a single feature component under `{frontend}/components/upload/` (matching where `SchemaMappingStep.tsx` already lives) rather than moving it to a new folder — this is a rework, not a new feature area.
- **Service pattern**: no class-based frontend services — add `suggestMapping`/`confirmMapping` as named functions in `lib/api.ts` alongside the other mapping/TDM functions from Stories 1.2/1.3.
- **State management**: local component state via hooks, `loading`/`error` flags around the `suggestMapping` fetch on mount, matching the pattern already used in `templates/page.tsx` and expected of `SchemaMappingStep.tsx`'s rework.
- **Backend architecture**: layered — the confirm endpoint stays a thin router function; the persistence/upsert logic (mapping_history keyed by signature, category_value_map storage) belongs in `mapping_service.py` next to `suggest_mapping`, not inlined in the endpoint.
- **Error handling (backend)**: `HTTPException(404, ...)` for missing dataset/TDM, `HTTPException(422, ...)` for an invalid `target_key` not belonging to the TDM, `HTTPException(500, detail=str(e))` for unexpected errors after `logger.exception(...)`.
- **API response format**: no global envelope; confirm should return a flat object echoing the dataset id and new `import_status`, e.g. `{"dataset_id": 12, "import_status": "mapped", "message": "Mapping confirmed"}`, consistent with other action endpoints in this API (`{"dataset_id": 12, "message": "..."}` style seen in `upload.py`/`analysis.py`).
- **Styling**: Tailwind utility classes with the existing semantic tokens (`bg-surface-container-low`, `text-on-surface-variant`, etc.) and Material Symbols icons already used throughout `SchemaMappingStep.tsx` — match the existing visual language exactly (badge chips, rounded-3xl cards) rather than introducing a new style.

### Tech Stack

- Next.js 14.2.35 / React 18 / TypeScript ^5 on the frontend; FastAPI + async SQLAlchemy on the backend, same as Stories 1.1–1.3.
- No new dependencies expected for this story — it consumes the mapping-suggestion service (Story 1.3) and TDM CRUD (Story 1.1/1.2) already in place.
- Testing: pytest/httpx for the confirm endpoint; Jest + Testing Library for the reworked wizard stage.

### Notes from Previous Stories

- Story 1.1 provides `dataset_mappings`, `mapping_history` tables and `datasets.tdm_id`/`import_status` columns — this story is the first to write to `dataset_mappings` and the second consumer (after Story 1.3's reads) of `mapping_history`.
- Story 1.2 provides the TDM table editor and its column-type/validation editing UI — reuse its "add column" sub-UI for this story's inline "Create new column" (Task 4.1) instead of building a second column-creation form.
- Story 1.3 provides `suggest_mapping()`, the `{source_column, target_key, confidence, layer}` proposal shape, and the shared header-signature function — this story is the primary UI consumer and the second backend writer (confirm) that must key off the same signature function.
- Story 1.3's default confidence threshold (0.60) determines which proposals arrive pre-selected vs. `target_key: null` (unmatched) — the UI must handle both cases (Task 3.2/3.3), it should not assume every proposal has a target.
