# Story 5.2: Pipeline entity & unattended execution

## Status

Approved

## Story

**As a** platform operator,
**I want** to compose input connector + TDM + saved mapping + output connector into a pipeline,
**so that** recurring imports run automatically.

## Acceptance Criteria

1: `pipelines` + `pipeline_executions` tables; setup flow mirrors Ingestro: name → input connector → target data model → output connector (+ output format `csv | json | xlsx`); a pipeline is only creatable when at least one confirmed mapping (header signature) exists for the chosen TDM, otherwise the UI directs the user to run one interactive import first
2: An execution runs the import stages unattended: header auto-detect (Epic 2), historical mapping (Epic 1), deterministic cleaning only — no LLM calls by default (config can enable them); results are written through the output connector in the chosen format
3: If unresolved required-column errors exceed the configured threshold, the execution pauses with status `needs_review`, appears in the review queue, and resumes through the interactive Review Entries flow (Epic 4); completing writes to the output connector as usual
4: Pipelines list page shows name, created by, execution count, last status, and history; filters for status/mode; a manual "Run now" trigger and an API trigger endpoint (token-authenticated) exist
5: Executions write the same lineage records as interactive imports (NFR4); a failed execution records the failing stage and error

## ⚠️ Naming collision — read before modeling tables

This codebase **already has a `PipelineRun` model and `pipeline_runs` table** (`{backend}/app/models/pipeline_run.py`) representing one run of the existing 5-task Celery **detection** chain (`preprocess → detect → fix → report → export`) for a single dataset — nothing to do with the "pipeline" concept in this story (a saved, reusable connector→TDM→mapping→connector recipe that can execute repeatedly). To avoid confusing the two: this story's new tables are named `pipelines` (the saved definition) and `pipeline_executions` (one run of that definition) — **never** call either of them `PipelineRun`/`pipeline_run` in code, comments, or the API, and note in the model docstrings that `pipeline_executions.detection_pipeline_run_id` (or similar) links an execution to the existing `PipelineRun` row it eventually triggers once the import stages complete.

## ⚠️ No JWT auth exists — read before implementing the API trigger

Epic 5's Additional Notes say "the API trigger token should reuse the platform's existing auth (JWT) rather than introducing Ingestro-style product license keys." **This auth does not currently exist.** `{backend}/app/core/config.py` has `JWT_SECRET_KEY`/`JWT_ALGORITHM`/`ACCESS_TOKEN_EXPIRE_MINUTES` fields, but grepping the entire backend confirms: no `python-jose`/`PyJWT` dependency in `requirements.txt`, no token-issuance endpoint, no auth dependency applied to any route anywhere in this API (`coding-standards.md`'s own audit confirms this: "authentication enforcement on endpoints (JWT settings exist in config but no auth dependency is applied to routes)"). This story is the **first real consumer** of those JWT settings. Scope accordingly — this is new infrastructure, not a reuse of something already working.

  - [ ] Subtask 1.3 Alembic migration for both tables — blocked on Epic 1 Story 1.1's chain repair; coordinate ordering with Story 5.1's `connectors` migration if landing in the same window
- [ ] Task 2 — Pipeline creation gate (AC: 1)
  - [ ] Subtask 2.1 `POST /api/v1/pipelines` (new `{backend}/app/api/endpoints/pipelines.py`) validates: `input_connector_id`/`output_connector_id` exist and have the correct `type` (`input`/`output` respectively, from Story 5.1), `tdm_id` exists, and — the key gate — **at least one confirmed `mapping_history` row exists for that `tdm_id`** (query Epic 1's `mapping_history` table, reusing the shared header-signature/mapping-history query logic from `{backend}/app/services/mapping_service.py` rather than re-querying ad hoc); if none exists, reject with `HTTPException(422, detail="No confirmed mapping exists yet for this Target Data Model — run one interactive import first.")`, matching the AC1 UI-direction requirement
- [ ] Task 3 — Unattended execution orchestration (AC: 2, 3)
  - [ ] Subtask 3.1 New `{backend}/app/services/pipeline_execution_service.py` (or a Celery task module `{backend}/app/tasks/pipeline_execution_tasks.py`, registered in `celery_app.py`'s `include` list alongside `pipeline_tasks`) implementing `run_execution(pipeline_id, source_object) -> PipelineExecution`: creates a `Dataset` row from the connector-provided file (reusing Story 2.1's format-detection/upload logic against the fetched bytes rather than requiring an actual HTTP upload), then chains: header auto-detect (Epic 2 Story 2.3's `detect_header_row`) → historical mapping only (Epic 1 Story 1.3's `suggest_mapping`, but **skip the LLM layer entirely by default** — this is a stricter version of Epic 1's `AI_MAPPING_ENABLED` flag scoped to unattended runs specifically, since a human isn't present to review an LLM guess; only enable it if the pipeline's own `config` explicitly opts in, per AC2). **Concretely, pass the per-call parameter Story 1.3 Subtask 7.1 now exposes: `suggest_mapping(db, dataset_id, tdm_id, ai_enabled=pipeline.config.get("enable_ai_for_unattended", False))`. Do NOT mutate the global `settings.AI_MAPPING_ENABLED` at runtime to achieve this — that flag is process-global and would leak across concurrent interactive requests; the `ai_enabled` parameter is exactly the seam added to 1.3/3.2 to make per-pipeline override safe. Likewise pass `ai_enabled=<same value>` into Story 3.2's LLM-fixer function.** → auto-confirm the mapping if it's a full header-signature match (confidence 1.0, same historical-layer logic Epic 4 Story 4.3's quick-mode path already established) → deterministic cleaning only (Epic 3 Story 3.2's rule-based fixers, **no LLM fixer calls**, no Prompts) → check required-column errors against the pipeline's configured threshold
  - [ ] Subtask 3.2 If required errors are within threshold: proceed to Epic 4 Story 4.2's complete-import logic (canonical Parquet + launch the existing detection `PipelineRun`/Celery chain), record `detection_pipeline_run_id`, then once the detection chain completes, write its output through the output connector (Task 4) and mark `PipelineExecution.status = "completed"`
  - [ ] Subtask 3.3 If required errors exceed threshold: set `PipelineExecution.status = "needs_review"`, `current_stage` to wherever it stopped, and **do not** proceed to complete-import — leave the dataset in its current `import_status` so a human can open it directly in Epic 4's Review Entries grid; do not build a separate "review queue" table for this — a `needs_review`-status `PipelineExecution` list (filtered from the existing `pipeline_executions` table) is the review queue; deliberately avoid naming anything here `ReviewQueue`/`review_queue`, since that table already exists (Epic 7, a completely different post-detection concept) and reusing the name would be confusing even if the schema were different
  - [ ] Subtask 3.4 When a paused execution is resumed (a human completes the Review Entries flow and hits "Complete import" per Epic 4 Story 4.2), that story's complete-import endpoint should detect it was triggered from a paused `PipelineExecution` (e.g. via a `pipeline_execution_id` reference on the dataset, or a lookup by `dataset_id`) and transition that execution's status to `running`→`completed` and continue to the output-connector write (Task 4) — this is a coordination point between this story and Epic 4 Story 4.2's endpoint; document it clearly so Story 4.2 (if implemented first) doesn't need to be revisited blindly
  - [ ] Subtask 3.5 Failure at any stage: catch, set `PipelineExecution.status = "failed"`, record `current_stage` (where it failed) and `error_message`, following the existing `_update_pipeline(..., status="failed", error_message=...)` convention from `pipeline_tasks.py`
- [ ] Task 4 — Output connector write (AC: 2)
  - [ ] Subtask 4.1 On successful completion, format the canonical/result data per the pipeline's `output_format` (`csv`/`json`/`xlsx` — reuse pandas' `to_csv`/`to_json`/`to_excel`) and write it via the output connector's implementation (Story 5.1's `minio_s3_connector.py` for now; other kinds return the same "not yet implemented" response as Story 5.1 if somehow selected as an output)

  - [ ] Subtask 5.2 **API trigger endpoint (token-authenticated)** — since no JWT infrastructure exists (see warning above), this story must build it from scratch: add a JWT library (`python-jose[cryptography]` — pairs with the already-present `cryptography` dependency — or `PyJWT`; pick one and add it to `{backend}/requirements.txt`) and a minimal token-issuance/verification module (e.g. `{backend}/app/core/security.py`) using the existing `JWT_SECRET_KEY`/`JWT_ALGORITHM`/`ACCESS_TOKEN_EXPIRE_MINUTES` settings that currently sit unused. Add `POST /api/v1/pipelines/{id}/trigger` guarded by a new `Depends(verify_api_token)` FastAPI dependency (the **first** auth dependency applied to any route in this API — flag this prominently in the PR since it's a first-of-its-kind change, not a small addition) validating a bearer token

## Dev Notes

### Relevant Source Tree

- `{backend}/app/models/pipeline_run.py` + `{backend}/app/tasks/pipeline_tasks.py` — the **existing, unrelated** detection-pipeline-run concept this story's `PipelineExecution` links to (via `detection_pipeline_run_id`) but must never be confused with or renamed to overlap.
- `{backend}/app/core/config.py` — `JWT_SECRET_KEY`, `JWT_ALGORITHM`, `ACCESS_TOKEN_EXPIRE_MINUTES` — present but **completely unused** until this story; also add the unattended-execution AI-off-by-default handling here or in the pipeline's own `config` JSON (per-pipeline override, not a single global flag, since AC2 says "config can enable them" per pipeline).
- `{backend}/app/services/mapping_service.py` (Epic 1 Story 1.3) — `suggest_mapping()`, `compute_header_signature()`, and the historical-match layer this story's execution orchestration calls directly (not via the HTTP endpoint) for auto-mapping.
- `{backend}/app/services/header_detection_service.py` (Epic 2 Story 2.3) — `detect_header_row()`, called directly for unattended header auto-detect.
- `{backend}/app/services/cleaning_service.py` (Epic 3 Story 3.2) — rule-based fixers, called with the LLM layer explicitly skipped for unattended runs by default.
- Epic 4 Story 4.2's complete-import logic and Story 4.3's quick-mode auto-confirm orchestration — this story's execution flow is structurally the same "auto-map → auto-clean → auto-confirm" sequence Epic 4 Story 4.3 already built for the quick-mode path; reuse those functions directly rather than re-deriving the sequence, and coordinate the "resume a paused execution" hand-off (Task 3.4) with Epic 4 Story 4.2's endpoint.
- `{backend}/app/models/review_queue.py` — the **existing, unrelated** Epic 7 post-detection review table; this story deliberately does not reuse or rename anything to look like it, per the naming-collision warning above.
- `{backend}/app/core/celery_app.py` — `include=["app.tasks.pipeline_tasks"]` — if this story adds a new Celery task module for execution orchestration, it must be added to this `include` list or the worker won't register it (the existing `agent_fix_task.py` module appears to rely on being imported some other way — verify how tasks actually get registered in this worker before assuming `include` is exhaustive, and don't silently repeat whatever gap may already exist there).

### Patterns & Conventions

- **Backend architecture**: `pipelines.py` endpoint (thin) → `pipeline_execution_service.py` (orchestration, calling into Epic 1/2/3/4's existing services directly, not via HTTP self-calls) → `models/pipeline.py`/`pipeline_execution.py`.
- **Reuse over reimplementation**: this story is almost entirely composition of Epics 1–4's already-built functions (mapping, header detection, cleaning, complete-import) — the main new code is the connector-sourced-file intake, the pause/resume state machine, and the JWT trigger auth. Resist the temptation to reimplement any of the reused pieces "for unattended context" — call the same functions with different parameters (`ai_enabled=False` by default). **This depends on Stories 1.3 and 3.2 exposing an `ai_enabled: bool | None = None` parameter (defaulting to `settings.AI_MAPPING_ENABLED` when `None`) rather than reading the global flag internally with no override. That parameter is a hard prerequisite for this story — if 1.3/3.2 are implemented without it, this story cannot force AI off per-pipeline without a global mutation, and must be treated as blocked until they add it.**
- **Config-driven behavior**: needs_review threshold and unattended-AI-enable are per-pipeline config (JSON column), not global settings, since different pipelines may want different tolerances — this is a slight departure from the single-global-flag pattern used elsewhere (`AI_MAPPING_ENABLED`, `QUICK_MODE_ENABLED`) and should be called out as such in code comments.
- **Error handling**: `HTTPException(404, ...)` missing pipeline/execution; `HTTPException(422, ...)` for the creation-gate rejection; `HTTPException(401, ...)`/`HTTPException(403, ...)` for the new token-auth dependency (Task 5.2) — this is the first place in the API these status codes would be used for their canonical auth meaning.
- **API response format**: no global envelope; flat objects/arrays consistent with the rest of the API.

### Tech Stack

- **Backend**: FastAPI >=0.110.0, async SQLAlchemy >=2.0.29, Celery[redis] >=5.3.0 (new execution-orchestration task(s), registered in `celery_app.py`), Alembic >=1.13.1.
- **New dependency**: a JWT library (`python-jose[cryptography]` recommended, pairs with the already-present `cryptography>=42.0.0`) — add to `requirements.txt`; this is the first JWT-issuing code in the project despite `Settings` having had JWT fields since early on.
- **Testing**: pytest/pytest-mock/httpx; mock connector I/O and the detection Celery chain in execution tests; real (not mocked) JWT encode/decode in the auth tests since that's exactly what's being verified.

### Notes from Previous Stories

- Epic 1 Story 1.3 (mapping), Epic 2 Story 2.3 (header detection), Epic 3 Story 3.2 (deterministic cleaning), Epic 4 Story 4.2 (complete-import/canonical Parquet) and Story 4.3 (quick-mode auto-confirm orchestration) are all directly reused, not reimplemented, by this story's unattended execution flow.

- Framework: pytest + pytest-mock + httpx `AsyncClient`, per established conventions; mock all connector I/O and the detection Celery chain launch.
- Test types required: creation-gate validation, full unattended happy-path execution, needs_review pause/resume, failure-path recording, lineage parity, and dedicated JWT-auth tests (issuance, valid/invalid/expired/missing token handling) — treat the auth tests with the same rigor as Epic 3 Story 3.3's security-sensitive test suite, since this is also genuinely new, security-relevant code.
