# Story 3.1: Cell-level validation engine

## Status

Draft

## Story

**As a** data operator,
**I want** validation errors reported per cell against the TDM,
**so that** I can see exactly what is wrong and where.

## Acceptance Criteria

1: A validation engine (evolving `{backend}/app/services/validation_service.py`) checks mapped data against the TDM and supports all PRD FR1 validation types: missing-required, type mismatch per `columnType` (incl. `email`, `phone`, `date` with `outputFormat`), `regex` with custom `errorMessage`, `unique`, unknown `category` value, and cross-column `required_with` / `required_with_all`
2: Issues are persisted to a new `import_issues` table as `{dataset_id, row, column_key, issue_type, raw_value, message}`; a summary endpoint returns per-column and per-issue-type counts
3: A 50k-row dataset validates within the NFR3 budget (≤ 10 s), verified by a performance test
4: The existing `POST /api/v1/{dataset_id}/validate` endpoint (`{backend}/app/api/endpoints/validate.py`) is reimplemented on the new engine without breaking its response contract (regression test with the current Upload Wizard payloads)
5: Re-validation can target specific rows/columns (used later by grid edits) instead of always re-running the full dataset

## Dev Notes

### Relevant Source Tree

- `{backend}/app/services/validation_service.py` — **the file this story evolves**. Contains the static `_RULE_SETS` catalogue (4 rule sets, already seeded as TDMs by Epic 1 Story 1.1), `validate_dataframe(df, column_configs, rule_set)` (existing engine: column-level required/type/range/categorical/regex checks plus rule-set row-level operator checks `>`, `<`, `not_in`, `regex`), and helpers `_is_numeric_col`, `_safe_float`. This story adds a new TDM-aware function alongside these — it does not replace them, since the legacy/quick-mode flow (NFR5) must keep working.
- `{backend}/app/api/endpoints/validate.py` — the endpoint this story reimplements internally. Current flow: `db.get(Dataset, ...)` → optional `get_rule_set(rule_set_id)` → `minio_service.get_file_stream()` + `pd.read_csv()` → `validate_dataframe()` → `ValidateDatasetResponse`.
- `{backend}/app/schemas/validation.py` — `ColumnConfig`, `ColumnConfigItem` (FE array shape with `.to_column_config()`), `ValidateDatasetRequest`, `ValidationError` (`row, column, message, severity`), `ValidationSummary`, `ValidateDatasetResponse` — these Pydantic shapes are the **existing response contract** AC4 requires preserving; extend with new TDM-related fields only additively, never by renaming/removing existing fields.
- `{backend}/app/models/data_fix_log.py`, `{backend}/app/models/review_queue.py` — existing precedent for issue/fix-log table shape and indexing style (`Index("idx_...", "col1", "col2")`) to mirror for the new `ImportIssue` model — note these two tables belong to a **separate, already-shipped "Epic 7" post-detection anomaly-fix system** (see Patterns & Conventions below) and are not to be reused or extended for this story's import-time validation issues; they're referenced here purely as a modeling-style precedent.
- Epic 1 Story 1.1 — provides the `TargetDataModel`/`TdmOut` schema (`key, label, columnType, validations, dropdownOptions`) this story validates against, and `dataset_mappings` (confirmed source→target column mapping) needed to know which source column backs each TDM column.
- Epic 1 Story 1.1's Alembic chain repair — hard prerequisite for this story's new migration.

### Patterns & Conventions

- **Backend architecture**: extend `services/validation_service.py` in place (or add a clearly-named sibling module) rather than replacing it — this codebase's layered convention keeps validation logic out of the endpoint (`api/endpoints/validate.py` stays a thin router).
- **Important distinction — two separate "fix" systems already exist in this codebase, neither of which this story touches**: (1) `{backend}/app/api/endpoints/review.py` + `models/review_queue.py` + `models/data_fix_log.py`, an already-shipped "Epic 7" human-review queue for **post-detection anomaly fixes** (operates on `AnalysisResult.anomaly_scores`, not import-time validation); (2) `{backend}/app/tasks/agent_fix_task.py` + `{ai_services_detection}/src/agent/*` (Celery-based, Redis-cached Gemini agent), also post-detection. This story's `import_issues` table and TDM validator are a **new, separate, pre-pipeline** concern (import-time schema/format validation before the ML detection pipeline ever runs) — do not conflate the two or attempt to unify their tables/models.
- **Error handling**: `HTTPException(404, ...)` for missing dataset; unexpected errors via `logger.exception` + `HTTPException(500, detail=str(e))`, matching `validate.py`'s existing `try/except/finally` around the MinIO stream.
- **Performance**: bulk-insert patterns for `import_issues` (avoid per-row commits); grouped SQL aggregation for the summary endpoint rather than in-Python counting — required to hit the NFR3 ≤10s/50k-rows budget.
- **API response format**: no global envelope; keep `ValidateDatasetResponse`'s existing flat shape; the new summary endpoint returns a flat nested-dict object, consistent with other summary-style endpoints in this API (e.g. `dashboard.py`'s summary shape).
- **Logging**: `get_logger(__name__)`, `%`-style lazy formatting, matching the rest of `validate.py`/`validation_service.py`.

### Tech Stack

- **Backend Framework**: FastAPI >=0.110.0, async SQLAlchemy >=2.0.29 for the endpoint layer, MySQL 8.0.35.
- **Migrations**: Alembic >=1.13.1 — chain repair from Epic 1 Story 1.1 is a hard prerequisite.
- **Data Processing**: pandas >=2.2.1 for validation logic (dtype checks, regex via `.str.match`, `pd.to_datetime` for date/`outputFormat` checks, duplicate detection via `.duplicated()`).
- **Testing**: pytest / pytest-mock >=8.1.1, httpx >=0.27.0 test client, following the `AsyncClient` + `dependency_overrides[get_db]` + `mocker.patch(...)` pattern already used in `tests/test_upload.py`; `tests/conftest.py`'s module stubs (minio, sqlalchemy, alembic, aiomysql) apply here too.
