# Story 3.4: Session undo/redo & lineage record

## Status

Draft

## Story

**As a** data operator,
**I want** to undo mistakes and see what was changed,
**so that** cleaning is safe to explore.

## Acceptance Criteria

1: Undo/redo works across all mutation kinds in an import session — suggestion applications, prompt applications, and manual cell edits — in strict reverse order
2: A lineage record per import (NFR4) is assembled from: source file → sheet → header config → confirmed mapping → ordered `transform_log` entries, sufficient to replay the import deterministically (LLM steps replayed from logged outputs, not re-queried)
3: The lineage is retrievable via API (`GET /api/v1/datasets/{id}/lineage`) and rendered as a simple timeline in the UI
4: Integration test: apply rule fix + LLM fix (mocked) + prompt + manual edit, undo twice, redo once — lineage and data state match expectations

## Tasks / Subtasks

- [ ] Task 1 — Undo/redo stack design (AC: 1) — **read this before implementing**
  - [ ] Subtask 1.1 **Manual cell edits (one of the three mutation kinds AC1 requires) are not implemented by any story before this one** — the manual-edit grid is Epic 4 Story 4.1, which explicitly depends on this story's "undo/lineage session" per Epic 4's own Dependencies section. This story must therefore design the undo mechanism **generically** around `transform_log` entries (already shared with Story 3.2's rule/LLM fixes and Story 3.3's prompt applications), with a `source` value (`rule|llm|prompt|manual`) that already reserves space for manual edits even though nothing produces `source="manual"` entries yet. Do not attempt to build the manual-edit endpoint in this story — that is out of scope (Epic 4) — but do verify the `TransformLog` schema (from Stories 3.2/3.3) has everything a future manual-edit writer would need (row, column_key, original_value, new_value, actor, applied_at) so Epic 4 can slot in without a schema change.
  - [ ] Subtask 1.2 Model the undo/redo stack as an ordered, per-`dataset_id` sequence over `transform_log` entries (ordered by `applied_at`/`id`) rather than a separate in-memory-only stack — since sessions may span page reloads and the wizard has no global client-side store, the durable source of truth for "what's been done, in order" should be the database, not client memory
  - [ ] Subtask 1.3 Undo of a single `transform_log` entry means: write `new_value` → back to `original_value` in the working data copy, mark the entry as "undone" by flipping the **`status` (`active|undone`) + `undone_at`** columns that **Story 3.2 Subtask 1.1 already defines in the canonical schema** (no new migration here — those columns are pre-reserved precisely so this story doesn't `ALTER` the table), and do **not** delete the log row — history must remain visible for the lineage timeline (AC3) even after undo. **Undo/redo operates at `operation_group` granularity when the entry has one** (a prompt application or bulk find-&-replace): undo the whole group atomically, per Story 3.3's single-unit requirement.
  - [ ] Subtask 1.4 Redo re-applies an undone entry in the same way, clearing its "undone" marker; a **new** mutation after an undo invalidates the redo stack beyond that point (standard undo/redo semantics — applying anything new while "back in history" discards the redone-but-abandoned branch), consistent with "strict reverse order" in AC1
- [ ] Task 2 — Undo/redo endpoints (AC: 1)
  - [ ] Subtask 2.1 Add `POST /api/v1/datasets/{id}/undo` and `POST /api/v1/datasets/{id}/redo` (new `{backend}/app/api/endpoints/lineage.py`, or extend `cleaning.py`/`prompts.py` if a single cleaning-session endpoint module already exists from Stories 3.2/3.3) — no request body needed; each operates on the next undoable/redoable `transform_log` entry for that dataset per Task 1.2/1.4's ordering
  - [ ] Subtask 2.2 After undo/redo, re-validate the affected cell(s) via Story 3.1's targeted re-validation so `import_issues` reflects the reverted/reapplied state
  - [ ] Subtask 2.3 404 if dataset not found; a well-formed no-op response (not an error) when there's nothing left to undo/redo, e.g. `{"undone": false, "reason": "Nothing to undo"}`
- [ ] Task 3 — Lineage assembly (AC: 2)
  - [ ] Subtask 3.1 Implement `assemble_lineage(db, dataset_id) -> LineageRecord` in a new `{backend}/app/services/lineage_service.py`, pulling: source file metadata (`Dataset.filename`, `storage_path`, upload timestamp — Epic 2 Story 2.1), selected sheet (Epic 2 Story 2.2's `selected_sheet`/interim structural field), confirmed header configuration (Epic 2 Story 2.3's header row/transpose/merge fields, same interim storage), confirmed mapping (Epic 1 Story 1.4's `dataset_mappings` for the dataset's `tdm_id`), and the full ordered `transform_log` for the dataset (including undone entries, marked as such, so the record shows the true history, not just the current end-state)
  - [ ] Subtask 3.2 For `source="llm"` and `source="prompt"` entries, the lineage record must carry what's needed to **replay without re-querying the LLM** (NFR4: "LLM steps replayed from logged outputs, not re-queried"). This is already provided by the **`replay_payload` (JSON)** column pinned in Story 3.2 Subtask 1.1 (the LLM's actual output / resolved operation plan) plus the per-cell `original_value`/`new_value` — so replay is deterministic from logged data alone. **Verify Stories 3.2/3.3 actually populate `replay_payload` (and per-cell values) at write time**; if a write path leaves it empty for an LLM/prompt entry, that's a bug in 3.2/3.3 to fix there, not a schema gap to patch here (the column already exists).
  - [ ] Subtask 3.3 Represent the assembled lineage as a Pydantic schema (`{backend}/app/schemas/lineage.py`), e.g. `LineageRecord{dataset_id, file, sheet, header_config, mapping, events: LineageEvent[]}` where each `LineageEvent` is one lifecycle step (upload, sheet-selected, header-confirmed, mapping-confirmed, plus one per `transform_log` entry in order)
- [ ] Task 4 — Lineage endpoint (AC: 3)
  - [ ] Subtask 4.1 Add `GET /api/v1/datasets/{id}/lineage` (new `lineage.py` endpoint module, or added to `datasets.py`) returning the `LineageRecord` from Task 3; 404 if dataset not found
- [ ] Task 5 — Frontend: timeline UI (AC: 3)
  - [ ] Subtask 5.1 Add a lineage timeline view (wherever the Review stage UI lives at this point in the epics — likely alongside the cleaning/suggestions UI from Story 3.2) rendering the ordered `events` list from the lineage endpoint as a simple vertical timeline (upload → sheet → header → mapping → each transform, with undone entries visually distinguished, e.g. struck-through or grayed)
  - [ ] Subtask 5.2 Add `getDatasetLineage(datasetId)`, `undoLastChange(datasetId)`, `redoLastChange(datasetId)` to `{frontend}/lib/api.ts`
  - [ ] Subtask 5.3 Add Undo/Redo buttons near the cleaning/suggestions UI, disabled appropriately when there's nothing to undo/redo (reflect the `{"undone": false, ...}` no-op response from Task 2.3 in the button's disabled state after a failed undo attempt, or better, have the frontend track available-undo-count from the lineage/undo-state response rather than guessing)
- [ ] Task 6 — Integration test (AC: 4)
  - [ ] Subtask 6.1 `{backend}/tests/test_undo_redo_lineage.py`: full sequence — apply a rule-based fix (Story 3.2), apply an LLM fix (Gemini mocked, Story 3.2), apply a prompt (Story 3.3, LLM-generated plan mocked), apply a manual edit (**write directly to `transform_log` with `source="manual"` in the test setup**, since no manual-edit endpoint exists yet — this test validates the undo/redo and lineage mechanism's handling of that mutation kind even though its producing endpoint is a future epic), then: undo twice, redo once, and assert both the working data state and the lineage record's event list/undone-markers match expectations at each step

## Dev Notes

### Relevant Source Tree

- `{backend}/app/models/transform_log.py` (**schema pinned in full by Story 3.2 Subtask 1.1**) — the table this story's undo/redo and lineage assembly both operate on. The `status`/`undone_at`, `operation_group`, and `replay_payload` columns this story relies on are **already defined there** — this story flips/reads them, it does **not** add a follow-up migration. If you find a genuinely missing column, fix it in Story 3.2's canonical definition, not with an `ALTER` here (per the single-definer rule and the migration-ordering note in Epic 1 Story 1.1).
- `{backend}/app/models/dataset.py` — `Dataset.tdm_id`, `import_status` (Epic 1), and the interim `selected_sheet`/header-configuration fields (Epic 2 Stories 2.2/2.3) — all direct inputs to lineage assembly. These were explicitly documented in Epic 2 as "populated here; consumed into the full lineage record by Epic 3 Story 3.4" — this is that consumption point.
- Epic 1 Story 1.4's `dataset_mappings` table — the confirmed mapping segment of the lineage record.
- `{backend}/app/services/validation_service.py` / Story 3.1's targeted re-validation — reused after every undo/redo to keep `import_issues` consistent with the reverted/reapplied data state.
- `{backend}/app/services/gemini_fix_service.py` and Story 3.3's `prompt_executor_service.py` — the LLM-sourced `transform_log` entries this story's lineage/replay logic must handle without re-calling the LLM (NFR4).
- Epic 4 Story 4.1 ("Review Entries grid") — the future producer of `source="manual"` transform_log entries; explicitly depends on "the undo/lineage session from Epic 3" per its own Dependencies — this story is what Epic 4 will plug into, not the other way around.

### Patterns & Conventions

- **Backend architecture**: new `lineage_service.py`, layered like the rest of `services/`; thin endpoints in a new or existing endpoint module.
- **Durable session state over client memory**: consistent with this codebase's general server-round-trip approach (NFR3 explicitly frames grid edits as "server round-trips async" rather than purely client-side state) — the undo/redo stack lives in the database (`transform_log` + its status marker), not in frontend memory, so it survives reloads and matches the no-global-store frontend convention.
- **Error handling**: `HTTPException(404, ...)` for missing dataset; well-formed non-error responses for "nothing to undo/redo" rather than treating that as a failure.
- **API response format**: no global envelope; `LineageRecord` is a flat nested object, `undo`/`redo` return small flat status objects.
- **NFR4 fidelity**: the entire point of this story is that logged outputs (not live re-queries) drive replay — double-check every LLM-sourced `transform_log` entry actually has enough persisted data (the applied value or operation plan) to satisfy this before considering the story done.

### Tech Stack

- **Backend**: FastAPI >=0.110.0, async SQLAlchemy >=2.0.29 for the endpoint layer; Alembic >=1.13.1 for any follow-up migration adding an undo-status column to `transform_log` (again blocked on Epic 1 Story 1.1's chain repair, same as every other migration in this PRD).
- **Testing**: pytest/pytest-mock/httpx, following the established `AsyncClient` + `dependency_overrides` + `mocker.patch` conventions; this story's integration test (Task 6) is the most complex in the epic and should mock all LLM calls (both `gemini_fix_service.py` and the prompt executor).

### Notes from Previous Stories

- Stories 3.1–3.3 in this epic define `import_issues` and `transform_log` and the rule/LLM/prompt mutation paths this story ties together — this story does not introduce new mutation-producing endpoints, only the undo/redo/lineage layer over what they already write.
- Epic 2 Stories 2.2/2.3 explicitly deferred full lineage assembly to this story ("populated here; consumed into the full lineage record by Epic 3 Story 3.4") — this is the story that fulfills that deferred promise; read those stories' `Dataset` field additions carefully rather than re-deriving sheet/header info from scratch.
- Epic 4 Story 4.1 (not yet built when this story ships) will be the first real producer of `source="manual"` transform_log entries — this story's test (Task 6.1) simulates that producer directly in test setup since the real endpoint doesn't exist yet; do not block this story on Epic 4.

### Testing

- Test file location: `{backend}/tests/test_undo_redo_lineage.py` (new).
- Framework: pytest + pytest-mock + httpx `AsyncClient`, per established conventions; mock all Gemini/Ollama and prompt-executor LLM calls.
- Test types required: unit tests for single undo/single redo/redo-stack-invalidation-on-new-mutation; the lineage-assembly unit test (correct ordering, correct segments, undone entries marked not removed); and the full AC4 integration test (rule fix + mocked LLM fix + prompt + manual edit, undo twice, redo once, assert both data state and lineage event list).
