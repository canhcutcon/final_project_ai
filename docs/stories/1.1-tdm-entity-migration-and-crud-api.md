# Story 1.1: TDM entity, migration & CRUD API

## Status

Draft

## Story

**As a** data operator,
**I want** to define and manage Target Data Models with typed columns and validations,
**so that** every import has an explicit canonical schema to map into.

## Acceptance Criteria

1: `target_data_models` table created via Alembic migration in `{backend}/alembic/versions/`; column definitions stored as ordered JSON in the Ingestro-compatible shape (`key`, `label`, `columnType`, optional `description`, `outputFormat`, `dropdownOptions` + `isMultiSelect`, `validations`)
2: Writes validate the JSON against the schema: supported `columnType` values are `string | int | float | date | email | phone | category | percentage | currency_code`; supported validations are `required`, `unique`, `regex` (+ `errorMessage`), `required_with`, `required_with_all`; a `category` column without `dropdownOptions` is rejected with a 422 and a field-level message
3: CRUD endpoints `GET/POST/PUT/DELETE /api/v1/tdm` (list, detail, create, update, delete) with pagination on list
4: The 4 existing rule sets in `{backend}/app/services/validation_service.py` (`real-estate-v1`, `commission-v1`, `invoice-v1`, `contact-v1`) are seeded as TDMs; existing `Template` records are data-migrated into TDMs and template endpoints keep responding as thin aliases (no frontend breakage)
5: Unit tests cover schema acceptance/rejection for representative definitions (valid full model, duplicate keys rejected, unknown columnType rejected, category without options rejected)

### Patterns & Conventions

- **Architecture**: layered — `api/endpoints` (routing only) → `services`/inline validators (business logic) → `models` (SQLAlchemy) with `schemas` (Pydantic) for request/response typing. Keep the TDM router thin; put JSON-schema validation logic in the Pydantic schema layer (`schemas/tdm.py`), not in the endpoint.
- **DB access mode**: this is an HTTP-endpoint feature → use **async** SQLAlchemy (`AsyncSession`, `Depends(get_db)`), matching `templates.py`, not the sync pattern used inside Celery tasks.
- **Error handling**: raise `fastapi.HTTPException(status_code=..., detail=...)` for known errors (404 not found, 409 duplicate name, 422 schema violation —422 is FastAPI's default for Pydantic validation errors, so prefer a Pydantic validator over a manual raise where possible to get the standard `{"detail": [...]}` shape). Unexpected errors: catch, `logger.exception(...)`, re-raise as `HTTPException(500, detail=str(e))`.
- **Validation**: request bodies are Pydantic `BaseModel`s in `schemas/`; there is no project-wide custom exception hierarchy — rely on Pydantic validators + `HTTPException`, consistent with existing code.
- **API response format**: no global envelope. Success responses are endpoint-shaped plain dicts (e.g. `{"tdm_id": 12, "message": "..."}` style for actions is optional — list/detail should return the flat resource shape like `_serialize(template)` does). List endpoint returns a bare JSON array (or array + minimal `limit` pagination per existing convention — no cursor/total-count envelope exists elsewhere in this codebase, don't invent one). Errors follow FastAPI default `{"detail": "<message>"}`.
- **Naming/style**: Python 3.10+, 4-space indent, type hints (`-> dict[str, Any]`), `snake_case.py` filenames, logging via `get_logger(__name__)` from `{backend}/app/core/logger.py` using `%`-style lazy formatting, never f-strings inside `logger.*` calls.
- **Import ordering**: `__future__` first (if used), then stdlib, then third-party, then `app.*` local imports.
- No authentication is enforced on any existing route (JWT settings exist in `app/core/config.py` but no auth dependency is applied) — do **not** add auth to the TDM routes; stay consistent with the rest of the API.

### Tech Stack

- **Backend Framework**: FastAPI >=0.110.0 (async, `Depends`), Uvicorn[standard] for serving.
- **Validation**: Pydantic v2 / pydantic-settings >=2.2.1 — use `model_validator`/`field_validator` (v2 API) for the category/dropdownOptions and duplicate-key checks.
- **Database**: MySQL 8.0.35 via SQLAlchemy >=2.0.29, async driver `aiomysql` for the endpoint layer.
- **Migrations**: Alembic >=1.13.1 — chain is currently broken (no committed `.py` sources under `versions/`, only stale bytecode for 11 revisions); repairing it is a prerequisite of this story, not optional groundwork.
- **Testing**: pytest / pytest-mock >=8.1.1, httpx >=0.27.0 as the FastAPI test client — add `test_tdm.py` under `{backend}/tests/`.

### Testing

- Test file location: `{backend}/tests/test_tdm.py` (mirrors existing `test_upload.py`, `test_database.py` naming).
- Framework: `pytest` with `httpx` as the async test client (see `{backend}/tests/conftest.py` for fixture setup) and `pytest-mock` where needed.
- Test types required: unit tests for the Pydantic schema validators (valid model accepted; duplicate key rejected; unknown `columnType` rejected; `category` without `dropdownOptions` rejected — all as 422s with field-level detail) **and** integration tests hitting the CRUD endpoints end-to-end (create → list → get → update → delete → 404-after-delete), plus a seed/migration assertion test that the 4 rule-set TDMs and migrated `Template` rows exist.
- Run with the project's existing `pytest.ini` config (`cd {backend} && pytest`).
