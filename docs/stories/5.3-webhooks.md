# Story 5.3: Webhooks

## Status

Draft

## Story

**As an** integrating developer,
**I want** webhook notifications for import/pipeline events,
**so that** downstream systems react without polling.

## Acceptance Criteria

1: `webhooks` table + CRUD (target URL, secret, subscribed events, active flag) with a limit of 10 per deployment; payloads are HMAC-SHA256 signed with the webhook secret (signature header documented)
2: Events emitted: `import.completed`, `import.needs_review`, `pipeline.completed`, `pipeline.failed` — each carrying ids, status, counts, and lineage reference
3: Delivery is async (Celery) with retry/backoff (e.g. 3 attempts) and a per-webhook delivery log (timestamp, status code, attempt) viewable in the UI
4: A documentation page lists payload schemas and the signature-verification recipe
5: Webhook dispatch failures never fail the import/pipeline itself (fire-and-forget with logging)

## Event-naming clarification (read before implementing)

Per Story 5.2's naming-collision warning: this codebase has an **existing** `PipelineRun`/`pipeline_runs` concept (the detection Celery chain) that is unrelated to Story 5.2's **new** `Pipeline`/`PipelineExecution` entities (the connector→TDM→mapping→connector recipe). This story's `pipeline.completed`/`pipeline.failed` events refer to **Story 5.2's `PipelineExecution` lifecycle** (an unattended execution finishing or failing), not the existing detection `PipelineRun`. `import.completed`/`import.needs_review` refer to the import/cleaning lifecycle (Epic 4's complete-import gate and Epic 5.2's needs_review pause) regardless of whether the import was interactive or unattended. Get this mapping right in the event-emission call sites (Task 3) — emitting from the wrong lifecycle would silently produce confusing webhook payloads.

- [ ] Task 1 — `webhooks` + `webhook_deliveries` tables (AC: 1, 3)
  - [ ] Subtask 1.1 `Webhook` ORM model (new `{backend}/app/models/webhook.py`): `id, target_url, secret (Text — stored as-is, not encrypted, since HMAC signing requires the raw secret at delivery time and this codebase has no existing encrypted-column precedent to build a decrypt-at-use path for; note this as a deliberate scope decision, and flag `secret` as write-mostly in the API the same way Story 5.1 treats connector credentials — never return it in `GET` responses even though it isn't encrypted at rest), subscribed_events (JSON array of event-name strings), active (bool, default True), created_at, updated_at`
  - [ ] Subtask 1.2 `WebhookDelivery` ORM model (new `{backend}/app/models/webhook_delivery.py`): `id, webhook_id (FK), event_type, payload (JSON), attempt_number, status_code (nullable), success (bool), error_message (nullable), delivered_at`, indexed on `webhook_id` — following the `Index(...)` style in `data_fix_log.py`/`review_queue.py`
  - [ ] Subtask 1.3 Alembic migration for both tables, coordinated with Stories 5.1/5.2's migrations (all blocked on Epic 1 Story 1.1's chain repair)
- [ ] Task 2 — CRUD with the 10-per-deployment limit (AC: 1)
  - [ ] Subtask 2.1 New `{backend}/app/api/endpoints/webhooks.py`: `GET/POST/PUT/DELETE /api/v1/webhooks`, following the `templates.py`/`connectors.py` thin-router pattern; `POST` checks `SELECT COUNT(*) FROM webhooks` first and rejects with `HTTPException(422, detail="Maximum of 10 webhooks per deployment reached.")` if already at the limit
  - [ ] Subtask 2.2 `subscribed_events` validated against the fixed enum (`import.completed`, `import.needs_review`, `pipeline.completed`, `pipeline.failed`) via a Pydantic validator — reject unknown event names rather than silently accepting them
  - [ ] Subtask 2.3 `secret` is write-only in responses (same `has_secret: bool` pattern as Story 5.1's `has_credentials`), even though it's not encrypted at rest (Task 1.1's scope note) — the API contract should look the same either way so a future move to encryption-at-rest doesn't change the response shape
- [ ] Task 3 — Event emission at the right lifecycle points (AC: 2)
  - [ ] Subtask 3.1 `import.completed`: emit from Epic 4 Story 4.2's complete-import endpoint on success (after canonical Parquet + pipeline launch), carrying `{dataset_id, import_status, lineage_url}` — this fires for **both** interactive and unattended (Story 5.2) completions, since both call the same complete-import logic
  - [ ] Subtask 3.2 `import.needs_review`: emit from Story 5.2's execution orchestration when it transitions a `PipelineExecution` to `needs_review`, carrying `{dataset_id, pipeline_execution_id, blocking_column_counts, lineage_url}`
  - [ ] Subtask 3.3 `pipeline.completed`/`pipeline.failed`: emit from Story 5.2's `PipelineExecution` completion/failure points (**not** the existing detection `PipelineRun`, per the naming clarification above), carrying `{pipeline_id, pipeline_execution_id, status, error_message?, lineage_url}`
  - [ ] Subtask 3.4 Each emission point calls a single `dispatch_webhook_event(event_type, payload_dict)` helper (new `{backend}/app/services/webhook_service.py`) rather than duplicating the "look up subscribed webhooks, queue a delivery task per webhook" logic at each of the four call sites
- [ ] Task 4 — HMAC signing + async delivery (AC: 1, 3, 5)
  - [ ] Subtask 4.1 In `webhook_service.py`, `dispatch_webhook_event()` looks up all `active` webhooks whose `subscribed_events` includes the given `event_type`, and for each, queues a new Celery task (`{backend}/app/tasks/webhook_tasks.py::deliver_webhook_task`, registered in `celery_app.py`'s `include` list) with the webhook id and payload — **queuing must never raise into the caller**: wrap the whole dispatch call in a `try/except` that only logs (per AC5, "fire-and-forget with logging"), consistent with the graceful-degradation convention already used for missing-Celery cases elsewhere (`start_analysis`'s `try/except` around `launch_pipeline`)
  - [ ] Subtask 4.2 `deliver_webhook_task` (Celery task, `bind=True, max_retries=3`, following the exact `self.retry(exc=exc)` pattern already used in `pipeline_tasks.py`/`agent_fix_task.py`): compute `signature = hmac.new(webhook.secret.encode(), json.dumps(payload, sort_keys=True).encode(), hashlib.sha256).hexdigest()` (stdlib `hmac`/`hashlib` — no new dependency needed), POST the payload to `webhook.target_url` with a documented header (e.g. `X-Webhook-Signature: sha256=<hex>`), and record a `WebhookDelivery` row for every attempt (including failed ones) with `status_code`, `success`, `error_message`
  - [ ] Subtask 4.3 On non-2xx response or connection error, retry per Celery's `default_retry_delay`/backoff (mirroring the `default_retry_delay=5`/`10` values already used elsewhere in this codebase's tasks) up to `max_retries=3`; after exhausting retries, leave the final `WebhookDelivery` row marked `success=False` and stop — this failure must never propagate back to whatever import/pipeline event triggered it, since the dispatch call (Task 4.1) is already fire-and-forget at the Celery-queuing level, and the task itself runs fully decoupled from the original request
- [ ] Task 5 — Delivery log UI (AC: 3)
  - [ ] Subtask 5.1 `GET /api/v1/webhooks/{id}/deliveries` (paginated) returning `WebhookDelivery` rows for a given webhook
  - [ ] Subtask 5.2 Frontend: webhook detail page (`{frontend}/app/(pages)/webhooks/[id]/page.tsx`, alongside a list page `webhooks/page.tsx` following `templates/page.tsx`'s pattern) showing a delivery log table (timestamp, event type, status code, attempt number, success/fail) for that webhook
- [ ] Task 6 — Documentation page (AC: 4)
  - [ ] Subtask 6.1 This codebase already exposes FastAPI's auto-generated OpenAPI docs at `/docs` (per `tech-stack.md`: "Async, OpenAPI docs at `/docs`") — define the four event payload shapes as proper Pydantic response models (e.g. `ImportCompletedPayload`, `ImportNeedsReviewPayload`, `PipelineCompletedPayload`, `PipelineFailedPayload` in `{backend}/app/schemas/webhook.py`) so their schemas are visible there automatically, rather than hand-writing a schema table that will drift from the real payloads
  - [ ] Subtask 6.2 The signature-verification recipe (compute HMAC-SHA256 over the raw payload bytes using the shared secret, compare to the `X-Webhook-Signature` header) can't be expressed as an OpenAPI schema — add a short, dedicated frontend page (e.g. `{frontend}/app/(pages)/webhooks/docs/page.tsx`) or a static markdown doc under `csv_agent_services/docs/` (this codebase's existing home for product-facing docs, per `source-tree.md`) with a code snippet (e.g. Python and Node examples) showing how to verify the signature — pick whichever fits the audience better (a frontend page is more discoverable for an integrating developer already using the product's UI; a markdown doc is cheaper to maintain) and be consistent with it
- [ ] Task 7 — Tests
  - [ ] Subtask 7.1 `{backend}/tests/test_webhooks.py`: 10-webhook limit enforcement, event-name validation, HMAC signature correctness (compute expected signature in the test and compare against what the delivery task produces), retry behavior on simulated failure (mock the HTTP call to fail twice then succeed, assert 3 `WebhookDelivery` rows), fire-and-forget guarantee (simulate a dispatch failure — e.g. Celery unavailable — and assert the calling import/pipeline flow completes successfully regardless)
  - [ ] Subtask 7.2 Explicit test for each of the four event types firing from its correct lifecycle point (Task 3), using mocked `dispatch_webhook_event` calls to assert the right event name + payload shape at each of the four call sites

## Dev Notes

### Relevant Source Tree

- `{backend}/app/tasks/pipeline_tasks.py`, `{backend}/app/tasks/agent_fix_task.py` — the established Celery task patterns (`bind=True`, `max_retries`, `default_retry_delay`, `self.retry(exc=exc)` in a `try/except`) to replicate exactly for `deliver_webhook_task`.
- `{backend}/app/core/celery_app.py` — `include=["app.tasks.pipeline_tasks"]` — the new `webhook_tasks` module must be added here (or registered via whatever mechanism actually makes `agent_fix_task` work today — verify before assuming, per Story 5.2's same note) for the worker to pick up the new task.
- `{backend}/app/api/endpoints/templates.py`, Story 5.1's `connectors.py` — the CRUD pattern (thin router, `_serialize()`, 404/409 `HTTPException`, write-only-secret handling) this story's `webhooks.py` follows closely, including the write-only-secret convention from Story 5.1's `has_credentials` flag (mirrored here as `has_secret`).
- Epic 3 Story 3.4's lineage endpoint (`GET /api/v1/datasets/{id}/lineage`) — the `lineage_url`/reference each webhook payload includes per AC2.
- Epic 4 Story 4.2's complete-import endpoint, Story 5.2's `PipelineExecution` orchestration — the four exact call sites for event emission (Task 3); this story does not change their internal logic, only adds a `dispatch_webhook_event(...)` call at each success/failure/pause point.
- No existing encrypted-secret-column precedent (Story 5.1 introduces one for connector credentials) — this story deliberately does **not** encrypt the webhook `secret` at rest (Task 1.1's scope note), which is an inconsistency worth flagging to whoever reviews this story's design, since Story 5.1 sets a precedent this story doesn't follow; if that's unacceptable, revisit using the same Fernet approach Story 5.1 introduces, at the cost of needing to decrypt on every delivery attempt.

### Patterns & Conventions

- **Backend architecture**: `webhook_service.py` (dispatch orchestration) + `webhook_tasks.py` (Celery delivery task) + thin `webhooks.py` endpoint, consistent with this codebase's layering.
- **Fire-and-forget via existing graceful-degradation convention**: this codebase already treats "the async side-system isn't available" as a non-fatal, logged condition in multiple places (`start_analysis`'s Celery-unavailable catch, `GeminiFixService`'s fallback chain) — webhook dispatch failure is another instance of exactly this pattern, not a new concept.
- **Retry/backoff**: mirror the existing `max_retries`/`default_retry_delay` values and `self.retry(exc=exc)` idiom already used in `pipeline_tasks.py`/`agent_fix_task.py` rather than inventing a different backoff scheme.
- **HMAC signing**: stdlib `hmac` + `hashlib.sha256` — no new dependency; sign the exact serialized JSON bytes that get sent, using a canonical serialization (`sort_keys=True`) so the documented verification recipe (Task 6.2) is unambiguous for integrators.
- **Error handling**: `HTTPException(422, ...)` for the 10-webhook limit and invalid event names; `HTTPException(404, ...)` missing webhook; delivery failures are recorded as data (`WebhookDelivery.success=False`), never raised as exceptions to any caller outside the Celery task itself.
- **API response format**: no global envelope; flat CRUD objects, `secret` write-only per the `has_secret` convention.

### Tech Stack

- **Backend**: FastAPI >=0.110.0, async SQLAlchemy >=2.0.29, Celery[redis] >=5.3.0 (new `webhook_tasks` module), Alembic >=1.13.1.
- **HTTP client for delivery**: `httpx` is already a dependency (>=0.27.0, currently used as the FastAPI test client) — reuse it for the actual outbound webhook POST inside the Celery task rather than adding `requests` as a second HTTP library.
- **Signing**: stdlib `hmac`/`hashlib`, no new dependency.
- **Testing**: pytest/pytest-mock, mocking the outbound HTTP call (never actually POST to a real URL in tests).

### Notes from Previous Stories

- Story 5.1's write-only-secret/`has_credentials` API convention is directly mirrored here as `has_secret` for webhook secrets.
- Story 5.2's `PipelineExecution` lifecycle is the source of `pipeline.completed`/`pipeline.failed` events and the `needs_review` pause that produces `import.needs_review` — get the event-source mapping right per the clarification note at the top of this story.
- Epic 4 Story 4.2's complete-import success path is the source of `import.completed` for both interactive and unattended (Story 5.2) imports alike.
- Epic 3 Story 3.4's lineage endpoint supplies the `lineage_url` reference every payload carries.

### Testing

- Test file location: `{backend}/tests/test_webhooks.py` (new).
- Framework: pytest + pytest-mock + httpx `AsyncClient` (endpoint tests) and mocked `httpx` calls (delivery task tests) — never hit a real external URL.
- Test types required: CRUD + limit + event-validation tests, HMAC signature correctness, retry/backoff behavior, fire-and-forget guarantee (the import/pipeline flow must succeed even when webhook dispatch fails entirely), and per-event-type emission-point tests.
