# Story 1.2: TDM UI (table + JSON views)

## Status

Approved

## Story

**As a** data operator,
**I want** to view and edit a TDM as a table or as raw JSON,
**so that** I can manage schemas in whichever form is faster.

## Acceptance Criteria

1: TDM list page (name, column count, updated date) and detail page in `{frontend}` with a toggle between table view and raw-JSON view
2: Paste-JSON-to-create: pasting a valid definition array creates the TDM; invalid JSON or schema violations surface inline errors pointing at the offending column/field
3: Table view supports column add/edit/delete/reorder, including validations and dropdown options for `category` columns
4: Copy button exports the full JSON definition; rename via inline edit on the title
5: Jest tests for the JSON-parse/validate reducer and the table-edit state logic

## Dev Notes

### Relevant Source Tree

- `{frontend}/app/(pages)/templates/page.tsx` — direct structural reference: local `useState` for list/loading/error, `useEffect` fetch-on-mount with a `cancelled` flag, busy-id pattern for row-level async actions (delete), `confirm()` before destructive actions.
- `{frontend}/components/templates/EditTemplateModal.tsx` — reference for an edit-form component receiving a record + save callback.
- `{frontend}/lib/api.ts` — single file holding all backend calls; `apiFetch<T>()` generic wrapper (sets `Content-Type: application/json`, prefixes `NEXT_PUBLIC_API_BASE_URL`, throws `Error("API Error: <status> <statusText>")` on non-OK). Add the new `Tdm*` functions here, not in a new service class.
- `{frontend}/types/upload.ts` — existing shared TS types (`ColumnConfig`, `Template`, etc.) to extend or sit alongside with `Tdm` types.
- `{frontend}/components/layout/SideNavBar.tsx` — add the new nav entry here.
- `{frontend}/app/(pages)/upload/` — existing 4-step wizard with `[id]` dynamic routes elsewhere in the app (`analyses/[id]`, `pipeline/[id]`, `reports/[id]`) — follow the same `[id]/page.tsx` convention for the TDM detail route.
- `{frontend}/__tests__/` — `api.test.ts`, `SideNavBar.test.tsx`, `TopAppBar.test.tsx` existing tests to mirror in structure and setup (`jest.config.ts`, `jest.setup.ts`).

### Patterns & Conventions

- **Component structure**: feature-based under `{frontend}/components/<feature>/`; PascalCase component files matching the exported component name. Small sub-components used only on one page are kept inline in that page file rather than extracted.
- **Pages**: live at `{frontend}/app/(pages)/<route>/page.tsx`; dynamic detail pages use `[id]/page.tsx`. All interactive pages need the `"use client"` directive.
- **Service pattern**: no class-based service layer — all backend access is functional, centralized in `lib/api.ts` as named async functions built on the single `apiFetch<T>` wrapper. Do not introduce a new abstraction (no axios, no service classes) for TDM calls.
- **State management**: no global store (no Redux/Zustand/Context). Use local component state (`useState`/`useCallback`/`useRef`/`useEffect`) with manual `loading`/`error`/`data` flags around each `apiFetch` call, exactly like `templates/page.tsx`.
- **Styling**: Tailwind CSS 3.4 utility classes inline in JSX; use semantic theme tokens already in use (`bg-surface`, `text-on-surface`, `font-body`) rather than raw colors; Material Symbols icon font is already loaded globally in `layout.tsx`.
- **Naming**: 2-space indent, functional components only, named exports for API helpers in `lib/api.ts`, default exports for page/components files.
- **Mock flag pattern**: several `lib/api.ts` functions honor `NEXT_PUBLIC_MOCK_VALIDATE` for UI-only development — not required for TDM endpoints (they're simple CRUD with no ML dependency), but be aware of the pattern if a reviewer asks for it.

### Tech Stack

- Next.js 14.2.35 App Router, React 18, TypeScript ^5 (strict).
- Tailwind CSS ^3.4.1 + PostCSS for styling.
- Fetch API via the `apiFetch` wrapper — no axios, no React Query/SWR.
- Testing: Jest ^30 + Testing Library ^16 + jsdom, configured via `{frontend}/jest.config.ts` / `jest.setup.ts`.
- No form library (react-hook-form/formik) is used anywhere in this codebase — build the table editor with native controlled inputs, consistent with the rest of the app.

### Notes from Previous Stories

- Story 1.1 defines the backend contract this story consumes: `GET/POST/PUT/DELETE /api/v1/tdm`, with the column-definition JSON shape `{key, label, columnType, description?, outputFormat?, dropdownOptions?, isMultiSelect?, validations?}` and 422 responses (FastAPI default `{"detail": [...]}` shape) for schema violations (duplicate `key`, unknown `columnType`, `category` without `dropdownOptions`). The client-side validator in Task 4.1 must mirror these exact rules so the UI can show errors before round-tripping to the API.
- Story 1.1 seeds 4 rule-set TDMs (`real-estate-v1`, `commission-v1`, `invoice-v1`, `contact-v1`) and migrates existing `Template` rows into TDMs — expect these to already appear in the list page once this story is implemented against a migrated backend.

### Testing

- Test file location: `{frontend}/__tests__/`, flat alongside existing tests (`tdmJson.test.ts`, `TdmColumnTable.test.tsx`).
- Framework: Jest + React Testing Library + jsdom, per `jest.config.ts`/`jest.setup.ts`.
- Test types required: unit tests for the pure JSON-parse/validate function (no rendering needed) and component/interaction tests for the table editor's add/edit/delete/reorder state transitions. No e2e test runner is present in this project — do not introduce one for this story.
